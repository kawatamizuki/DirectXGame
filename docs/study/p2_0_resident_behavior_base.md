# 住民行動の土台の変更(P2-0)

2026-11-09。商業エリア P2 の準備として、住民の行動の「土台」を変えた(仕様書の P2-0 だけ)。設計の表は [docs/design/resident_outing.md](../design/resident_outing.md) の §20。

## 1. 用語
| 用語 | 意味 |
|---|---|
| 外出の理由 | 外出を決めた後に選ぶ「なぜ出かけるか」。手軽 / がっつり / エリアの3つ。需要のカテゴリ(生活/余暇)とは別の軸で、距離の効き方・立ち寄りのしやすさを変える |
| 需要の段階 | 需要(0〜100)を、充足・不足・深刻・危機的の4段階に分けたもの。連続の値のまま掛けずに、段階ごとの補正を使う |
| 切迫度 | 「今、どれくらい切迫した需要があるか」を0〜1で表す1つの数。段階の切迫度 × カテゴリの重要度の最大値 |
| 重み付き抽選 | 重みを正規化して、1つの乱数で選ぶ。重みが0の候補は、選ばれない(= 他の候補から、同じ乱数で選び直すのと同じ) |
| 形 k | 距離の重み exp(-(道のり ÷ 目安)^k) の指数。k=1 が従来の指数。大きいと、近場は下がらず、目安を超えると急に下がる |
| 安全弁 | 立ち寄りの最大回数のように、「普通は届かないが、暴走を止める」ための上限 |

## 2. 設計で悩んだ点
- **「生活 50 / 余暇 10 → 生活が高い確率で選ばれる」を、どう満たすか**: 段階の補正を、カテゴリ共通の表にすると、余暇の「危機的」(補正が大きい)が、生活の「不足」(補正が小さい)に勝ってしまう。重要度(1.0 / 0.5)を掛けるだけでは、差が2倍にしかならず、8割には届かない。→ 補正の表を、**カテゴリごと**に持つ(生活 {0.06, 1.0, 1.6, 2.5}・余暇 {0.30, 0.40, 0.45, 0.50})。余暇は、段階が上がっても、あまり増えない(「あると嬉しい」需要)。結果は、生活 50 / 余暇 10 で生活が約79%(100%ではない)。全ての数値は設定で変えられる。
- **需要が両方足りている時の動き**: P1 は「自発的な外出は、余暇が7割」だった。段階の補正に「充足」の値を持たせて(生活 0.06・余暇 0.30 × 0.5)、同じ式で、余暇が約71%になるようにした。「状況ごとに別の式」を作らずに、既存の傾向を保てた。
- **理由とカテゴリを、独立にしない**: 理由の重みに、今の状態(需要の切迫・体力)を反映する。ただし、同じ効果を二重に掛けないように、**切迫度は、がっつりの重みに1回だけ**入れた(手軽には掛けない)。比で見ると、切迫すると「手軽」が相対的に増える。
- **移動で体力を消費しない**: P1 は、出る前に「往復の移動 + 利用」の体力を確かめ、迂回して帰る時にも消費していた。P2-0 では、移動の項を全部やめた(`staminaPerLegacyCell`・`roadLossStaminaCostScale`・`RoadLossStaminaCost`・`RequiredStaminaForWalk`・候補の `walkLength`)。体力を見る場所は、施設を選ぶ時(使う分)・外出判定(自発)・立ち寄りの確率だけ。帰宅の処理は、体力を見ない。
- **固定のしきい値を、連続的な重みにする**: 立ち寄りの「体力30以上」→ 体力の割合に比例する係数(0の時だけ、考えない)。「今の施設から8マス以内」→ 距離の重み(立ち寄り先は、距離の目安に0.6倍。設定で上限を置くこともできる)。除外は、本当に不可能な場合(家が無い・回数の上限・時刻・体力0・道が無い)だけにした。
- **乱数の消費を、状態で変えない**: 理由1・カテゴリ1・利用目的1・施設1を、いつも引く(重みが全て0でも、候補が0軒でも、理由の抽選は1回引く)。これは、記録・テストの強制が、乱数の列を変えない、という既存の原則と同じ。

## 3. 使った技術
- 重みを、`PickWeightedIndex`(既存)で選ぶ。理由・カテゴリも、同じ関数・同じ考え方。
- 計算の途中の値を、トレース構造体(`OutingReasonTrace`・`PurposeTrace`・`StopoverChanceBreakdown`・`FacilityWeightBreakdown`)に書き出し、画面は、それを見せるだけ(別の式で計算し直さない)。
- 「今、外出するなら」の見積りは、使い捨ての乱数(`SimRandom scratch(1)`)で、同じ関数を呼ぶ(重みは乱数に依らない)。ゲームの乱数列を進めない。
- 既定の引数で、既存の呼び出しを壊さない: `ComputeFacilityWeight(…, reason = Quick, distanceScaleFactor = 1.0)`。手軽の既定値(目安の倍率1.0・形1.0)は、従来の式と一致する。

## 4. 見つけた問題と、直し方
- **PowerShell のスクリプトで、日本語が文字化け**: テストの編集を、PowerShell 5 のスクリプトファイル(BOM無し)で行ったところ、日本語の文字列が、別の文字コードとして読まれて、壊れた。→ そのファイルを、`git checkout` で戻して、編集ツールでやり直した。日本語を含む編集は、スクリプトの文字列では行わない。`.ps1` を作る時は、BOMを付ける(`tests/run_tests.ps1` も、最初は、BOM無しで、構文エラーになった)。
- **テストの前提が、仕様の変更で、変わった**: 「遠すぎて体力が足りない」「往復の体力」「立ち寄りの体力30以上」「道路の迂回の体力」を前提にしたテストは、仕様どおり、書き換えた(消した・置き換えた)。**書き換えた理由を、テストのコメントに残した**。
- **旧い実装の写しとの比較テスト**: `sim_debug_recorder_test` には、段階1より前の実装の写しがあり、「新しい内訳の計算が、旧い計算と一致する」ことを確かめている。P2-0 で意図的に変わった関数(`ChoosePurpose`)の比較は、「乱数の消費・トレースの一致・重みの式」の検証に置き換えた。変わっていない部分(重み・施設の抽選・外出の確率)の比較は、写しを、新しい体力の規則に合わせて、残した。
- **Debug の exe が、起動中のゲームに掴まれて、リンクできない**: ユーザーのゲームを止めずに、出力先を別の場所にして(`-p:OutDir=`)、ビルド・実機確認を行った。

## 5. 確かめたこと
- 単体テスト(`tests/`、9本。新規 `sim_p2_0_test`): 需要の段階の境界(80/50/25)、切迫度、理由の重みの式・状態の反映(健康で体力満タン=がっつり44%、生活が危機的=11%、体力が少ない=14%)、エリアは候補が無い間は選ばれない、乱数の消費の固定、理由ごとの距離(がっつりは、遠くでも下がりにくい・形k・立ち寄りの倍率)、体力(施設の利用だけ・2軒目以降は高い・足りない施設は除外・遠くても除外されない)、立ち寄りの連続的な確率(体力・需要・理由・回数、3回目以降も可)、利用後に更新された需要でカテゴリを選び直す、**生活 50 / 余暇 10 → 生活が約79%**。
- ゲーム内(Debug、保存した街: 住宅6軒・施設4種×2、住民6人): 26週を進めて、異常0件・外出の立ち往生0件。22週時点の集計: 外出322回(手軽185・がっつり137・エリア0)、利用381回(主目的320 + 立ち寄り61)、立ち寄りの抽選341回のうち63回当選。決定論テスト(同じ状態から12週を2回進めて、指紋が一致するか): 一致。
- Debug・Release とも、警告・エラーなしでビルド。

## 6. まだ確かめていないこと・限界
- **体力0での帰宅**: 帰宅の処理に体力の確認が無いことは、コードで確かめた(体力を見る場所の一覧)。実機で、体力0の住民を帰宅させる試験は、していない。
- **P1との挙動の比較**: P1(P2-0の前)の同じ街での集計と、並べて比べていない。外出1回あたりの立ち寄り率・理由の分布は、設計の予想(立ち寄り 約16%・がっつり 約43%)に近いが、ゲームとして面白いかは、未確認。
- **手での操作**: 画面で、設定のスライダーを動かす・住民デバッグの新しい表示を読む、は、していない(ビルドは通っているが、見た目の確認はしていない)。
- **大きな街**: 住民6人の街だけ。規模が大きくなった時の、理由・カテゴリの分布は、見ていない。
- 数値は全て仮(重要度・段階の補正・理由の倍率など)。
