# 学習メモ: 派生データ・キャッシュ・状態の復元(ロード直後に商業エリアの所属が空になる問題)

## 1. 何が起きていたか
- 「施設 → 商業エリア」の対応表(`DemandSystem::m_areaOfFacility`)は、セーブしない。読み込みで空にされ、次の需要の計算(約3秒ごと)で作り直されていた。
- だから、ロードしてから最大約3秒、全ての施設が「どの商業エリアにも属さない」扱いになり、その間の施設の利用・立ち寄り・週末の評判の計算がずれていた。
- 見つけ方: 固定時間刻み(F2)の追加検証で、「セーブ→ロードしてから進めた街」と「そのまま進めた街」を比べたら、ずれる場合があった。最初にずれたステップの中身を比べると、ある住民の `areasCounted`(この外出で数え済みの商業エリア)が `[1]` か `[]` か、だけが違った。

## 2. 用語
| 用語 | 意味 |
|---|---|
| 正本(ソース・オブ・トゥルース) | 本当の値を持つデータ。セーブする物(建物の位置・敷地、商業エリアの四角) |
| 派生データ | 正本から計算し直せるデータ。ここでは「どの施設がどのエリアに属するか」 |
| キャッシュ | 派生データを、毎回計算しないで済むように、取っておいた物 |
| 無効化(インバリデーション) | キャッシュが古くなったので、もう使えない、と印を付けること |
| 遅延再構築 | 印が付いたキャッシュを、次に必要になる直前に作り直すこと |
| 状態の復元 | セーブしたデータから、ゲームの状態を元どおりにすること。派生データは「作り直して」元どおりにする |
| 往復テスト | 保存 → 読み込み をして、元と同じに動くかを確かめるテスト |

## 3. なぜ起きたか(キャッシュの「作り直す時」が足りなかった)
派生データをセーブしないのは、正しい設計(正本と食い違う危険が無い)。ただし、セーブしないなら、**読み込んだ後に、使う前に作り直す**必要がある。今回は、作り直す時が「需要の計算(約3秒ごと)」しか無かった。

| 時 | 前 | 後 |
|---|---|---|
| 読み込み(`Reset`) | 空にする | 空にして、**「作り直しが必要」の印を立てる** |
| 次の更新(`Update`)の最初 | 何もしない | **印があれば作り直す**(所属を使う処理より先) |
| 需要の計算(約3秒ごと) | 作り直す | 作り直す(同じ関数) |

## 4. 技術の選定(7項目)
### 4.1 問題と要求
読み込み直後から正しい所属で動かす。条件: ① 全ての読み込み経路(F9・Scenarioパネル・テストマップ・自動検証・再現・巻き戻し)に効く ② 所属の規則・住民AI・バランスは変えない ③ 所属を使う処理より先に作り直す ④ 読み込みの順番(住民 → 商業エリア)に左右されない。

### 4.2 候補・4.3 長所と短所
| 方式 | 長所 | 短所 |
|---|---|---|
| A. 読み込み完了の合図(`SetOnWorldReplaced`)で作り直す | 読み込み直後に確実 | ゲーム本体の配線に頼る。合図を通らない使い方で漏れる |
| **B. 印を立て、次の更新の最初に作り直す(遅延再構築)** | `DemandSystem` の中だけで完結。読み込みの順番に左右されない。画面を通らない経路でも効く | 「読み込み → 最初の更新」の間に読む処理があれば漏れる(今は画面の表示だけ) |
| C. 対応表もセーブする | 読み込み直後から正しい | 派生データを保存すると、正本と食い違う危険。セーブ形式が変わる |
| D. 住民の読み込み(`Load`)の中で作る | 単純 | 商業エリアは住民より後に読み込まれるので、前の街のエリアを使う(危険) |
| E. キャッシュをやめ、毎回計算 | ずれが起きない | 立ち寄りのたびに、全エリア×全施設の計算(重い) |

### 4.4 採用した理由
B。要求①〜④を全て満たし、変更は `DemandSystem` だけで済む。試作で、セーブ→ロードの往復テストが全て一致した。

### 4.5 採用しなかった理由
A は配線漏れの危険、C は正本と食い違う危険とセーブ形式の変更、D は読み込みの順番の問題、E は重さ。

### 4.6 根拠と、まだ確認できていない点
- 根拠: 読み込みの順番(`Core/Game.cpp:345-349`)、所属を使う全ての場所(週末の評判・利用の終わり・立ち寄り・統計の出力・画面)、往復テストの結果(下の5.)。
- 未確認: 住民が数百人の大きな街 / 編集モードで読み込んで、そのまま住民デバッグの「外出の理由の見積り」を見た時(表示だけ。最初の更新まで所属が空に見える)。

### 4.7 見直す条件
- 「読み込み → 最初の更新」の間に、所属を使う処理が増えたら → A を併用するか、読む関数の中で作り直す。
- 所属の計算が重くなったら(施設・エリアが非常に多い)→ 変わった所だけ作り直す仕組みを考える。

## 5. 修正と確かめ方
### 5.1 変えた所(`Simulation/DemandSystem.{h,cpp}` だけ)
```cpp
// 読み込み(Reset): 空にして、印を立てる(商業エリアは住民より後に読み込まれるので、ここでは作らない)
m_areaOfFacility.clear();
m_areaMembershipDirty = true;

// 次の更新の最初: 所属を使う処理より先に作り直す(一時停止中の更新でも)
if (m_areaMembershipDirty && context.objects) { RebuildAreaMembership(*context.objects); }

// 需要の計算でも、同じ関数で作り直す(結果が食い違わないように)
std::vector<AreaMembers> areaMembers = RebuildAreaMembership(*context.objects);
```
- 所属を作る処理を、`RebuildAreaMembership` 1つにまとめた。需要の計算の施設の一覧と、同じ条件(住宅・オフィスを除き、施設の種類だけ)・同じ並び。
- 所属の規則(`ComputeAreaMembers`。敷地の50%以上が中)は変えていない。

### 5.2 確かめ方
| 確認 | 修正前 | 修正後 |
|---|---|---|
| 往復テスト: 40ステップごとにセーブ→ロードし、400ステップ先の街を、そのまま進めた街と比べる(各街1491か所) | Test 1382、diag_rt2 935 | 両方 1491 |
| 一時停止中に読み込む・編集モード中に読み込む(各150か所) | (未計測) | 全て一致 |
| 再現条件(利用が終わる直前のセーブ。21022・51057 ステップ目) | ずれる | 一致 |
| 読み込み直後の所属 | 約3秒、空 | 最初の更新で、読み込む前と同じ6件 |
| F0 の基準の指紋(8つ) | ― | 変わらない(最初の3秒に、商業エリアに関わる出来事が無かったため) |

- 往復テストは「既知の違い」をそろえてから比べた(`visitHoursLeft` の負の端数。移動中の住民の値で、動きには影響しない)。
- 試作で「修正前と後」を測ってから、本番の修正を入れて、同じテストをもう一度回した(試作と本番で、結果が同じ)。
- 単体テスト: 所属の規則(敷地の50%以上など)は、既存の `tests/sim_area_test.cpp` が確かめている。今回の「作り直すタイミング」は、ゲームの中の往復テストで確かめた。

## 6. 気をつけること
- セーブしないデータを足したら、「読み込んだ後、いつ作り直すか」を必ず決める。
- 往復テストは、1か所だけでは足りない。位置をたくさん変えて試す(今回、1か所の確認では見つからず、1491か所で見つかった)。
- 建築・解体・エリアの変更の後に、所属が最大約3秒遅れて更新される問題は、別にある(今回は直していない)。
