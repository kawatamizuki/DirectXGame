自分用の学習資料です(提出物ではありません)。

## 1. 全体像

```
[素材フォルダ] → AssetCatalog(探す。読まない) → 一覧(パス・サイズ・更新日時…)
                                                  │
              AssetBrowser(ImGuiのパネル)──見えている項目を──→ ThumbnailCache
                                                                  │ 無ければ
                                                                  ▼
                       Model::LoadFromFile → ModelPreviewRenderer → OffscreenTarget(テクスチャに描く)
                                                                  │ 読み戻す(GPU→CPU)
                                                                  ▼
                              2x2で平均して縮小 → PNGに保存(Cache/Thumbnails/)→ GPUテクスチャ(SRV)
                                                                  │
                                      ImGui::Image でパネルに表示 ←──┘   (2回目以降は、PNGを読むだけ)
```
ポイントは3つです。
- **重い処理(モデルを読んで描く)を、1回だけ**にして、結果(画像)をディスクに残す。
- 重い処理は、**1フレームに少しずつ**行い、画面が止まらないようにする。
- パネルが**閉じている間は何もしない**(負荷ゼロ)。

## 2. 用語集

| 用語 | 意味 |
|---|---|
| サムネイル | 一覧表示用の小さな画像(ここでは128x128) |
| キャッシュ | 一度作った結果を保存しておいて、次から使い回す仕組み。ここでは `Cache/Thumbnails/` のPNG |
| キャッシュの無効化 | 元のデータが変わった時に、古いキャッシュを使わないようにすること |
| オフスクリーン描画 | 画面(ウィンドウ)ではなく、メモリ上のテクスチャに描くこと(render to texture とも言う) |
| RTV (Render Target View) | 「ここに描く」という描画先を表すビュー |
| DSV (Depth Stencil View) | 深度(手前か奥か)を書き込む先のビュー |
| SRV (Shader Resource View) | テクスチャを「読む」ためのビュー。シェーダーやImGuiが画像として使う |
| ステージングテクスチャ | CPUから読めるように作る、読み戻し専用のテクスチャ |
| 読み戻し(リードバック) | GPUが描いた結果を、CPU側のメモリへ取り出すこと。GPUの完了待ちが発生するので重い |
| RowPitch | GPUのメモリの1行ぶんの長さ(バイト)。幅×4より大きいことがある(行ごとに隙間がある) |
| ビューポート | 描いた絵を、描画先のどの範囲に出すかの設定 |
| スーパーサンプリング | 大きく描いてから縮小して、縁のギザギザ(ジャギー)を減らす方法 |
| ボックスフィルタ | 隣り合う画素の平均を取る単純な縮小方法(2x2の4画素の平均など) |
| WIC | Windows Imaging Component。Windows標準の画像の読み書きの仕組み(PNGなど) |
| COM | WICなどが使う、Windowsの部品の仕組み。`CoCreateInstance` で部品を作る |
| ハッシュ | 文字列などから、固定長の「指紋」のような数を作る計算。同じ入力なら必ず同じ値 |
| FNV-1a | 小さくて速い、定番のハッシュ計算の1つ |
| LRU(最近使われていない物から捨てる) | メモリが満杯の時に、一番長く使われていない物を捨てる方針 |
| 時間枠(フレーム予算) | 1フレームのうち、この処理に使ってよい時間(ここでは8ms) |
| 即時モード(Immediate mode) | ImGuiの方式。毎フレーム、画面の描き方を全部書き直す(部品を作って覚えさせない) |
| ListClipper | 一覧のうち、画面に見えている行だけを処理する仕組み(仮想化) |
| ガンマ補正 | 画面の明るさの特性(約2.2乗)に合わせて、色の値を変換すること |
| sRGB | 一般的な画面・画像で使う、ガンマ補正済みの色の表し方 |
| リニア(線形)空間 | 明るさが足し算で正しく計算できる色の表し方。ガンマ補正をしていない |
| UNORM / UNORM_SRGB | 0〜255を0〜1に対応させる形式。`_SRGB` は、読む時にsRGB→リニアへ自動変換する |
| MTL / Kd | OBJの材質ファイルと、その拡散色(物の基本の色) |
| 球面座標 | 中心からの「距離・横の角度・縦の角度」で位置を表す方法。モデルの周りを回るカメラに使う |
| 状態機械 | 設定(状態)を覚えていて、次の命令がその状態の影響を受ける仕組み。Direct3Dのデバイスコンテキストがこれ |
| スタブ(代用品) | テストで、本物の代わりに使う簡単な偽物 |

## 3. 使った技術の解説

### 3.1 オフスクリーン描画(テクスチャに描く)
画面に描く代わりに、**自分で作ったテクスチャ**に描きます。必要な物は3つです。
- 色を書く先 = RTV、深度を書く先 = DSV、描いた結果を読む窓口 = SRV(いずれも `OffscreenTarget` が持つ)。

```cpp
// Graphics/OffscreenTarget.cpp(要点)
colorDesc.BindFlags = D3D11_BIND_RENDER_TARGET | D3D11_BIND_SHADER_RESOURCE; // 描く先 かつ 読む元
device->CreateTexture2D(&colorDesc, nullptr, &m_colorTexture);
device->CreateRenderTargetView(...);   // 描く
device->CreateShaderResourceView(...); // ImGuiで表示する
```
**描画先の切り替えと復元**が重要です。Direct3Dのデバイスコンテキストは「今の描画先・ビューポート」を覚えている**状態機械**なので、切り替えたら必ず元に戻します。
```cpp
void OffscreenTarget::Begin(...)
{
    context->OMGetRenderTargets(1, &m_savedRtv, &m_savedDsv);   // 今の描画先を覚える
    context->RSGetViewports(&count, &m_savedViewport);          // 今のビューポートを覚える
    context->OMSetRenderTargets(1, &rtv, dsv);                  // 自分の描画先へ
    ...clear...
}
void OffscreenTarget::End(...)  { /* 覚えておいた物に戻す */ }
```
> 学び: 状態を変えたら「元に戻す」か「使う側が毎回自分で設定する」。後者が安全(下の4章のカリングの問題も同じ原因)。

### 3.2 GPUからCPUへの読み戻し
GPUのテクスチャはCPUから直接読めません。**ステージングテクスチャ**にコピーしてから `Map` します。
```cpp
context->CopyResource(m_staging.Get(), m_colorTexture.Get());
context->Map(m_staging.Get(), 0, D3D11_MAP_READ, 0, &mapped);   // ここでGPUの完了を待つ
// 行ごとに RowPitch の隙間があるので、1行ずつ詰め直す
for (y...) memcpy(&out[y * width * 4], mapped.pData + y * mapped.RowPitch, width * 4);
context->Unmap(...);
```
GPUの完了待ちが入るので重い処理です。**サムネイルを保存する時の1回だけ**使います(毎フレームは使わない)。

### 3.3 スーパーサンプリング(2x2の平均で縮小)
128x128の絵を直接描くと、斜めの線がギザギザになります。**256x256で描いて、4画素の平均で128x128に縮小**すると、縁がなめらかになります。
```cpp
out = (p00 + p10 + p01 + p11 + 2) / 4;   // 平均。+2 は四捨五入のため(整数の割り算は切り捨てなので)
```
テストで「0, 0, 0, 3 の平均=0.75 → 1 に四捨五入される」ことを確認しています。

### 3.4 PNGの保存(WIC)と、安全な書き込み
Windows標準のWICで、PNGに書き出します(外部ライブラリは増やさない)。
- `CoCreateInstance(CLSID_WICImagingFactory)` でWICの部品を作る(COM)。
- PNGエンコーダーの標準の並びは **B,G,R,A**。私たちのデータは R,G,B,A なので、RとBを入れ替えてから書く。
- **途中で失敗しても、既存のファイルを壊さない**ために、一時ファイル(`.png.tmp`)に書いてから、`MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)` で置き換える(アトミックな置き換え)。保存・読み込み機能(セーブデータ)と同じ考え方。

### 3.5 キャッシュの設計
**キー(どのモデルの、どの状態のサムネイルか)**
```
キー = FNV-1a64( パス | ファイルサイズ | 更新日時 | 見た目の版(kVersion) )   → 16桁の16進数
ファイル名 = <モデル名>_<キー>.png
```
- ファイルが変われば(サイズか更新日時が変わる)、**キーが変わる=別のファイルになる**ので、自動で作り直されます(古いPNGは残るが、使われない)。
- 見た目(カメラ・背景・光・色の扱い)を変えたら、`kVersion` を上げる(今回、色の扱いを直したので1→2に上げた)。
- ハッシュは `std::hash` ではなく、**自前のFNV-1a**。`std::hash` は実装やバージョンで値が変わるので、ファイル名に使うと、環境が変わった時に全部作り直しになるため。
```cpp
uint64_t hash = 14695981039346656037ULL;          // FNV-1aの初期値
for (unsigned char c : text) { hash ^= c; hash *= 1099511628211ULL; }  // 1文字ずつ: XOR してから素数を掛ける
```
**メモリ上の保持と、LRUによる削除**
- GPUのテクスチャ(SRV)は、最大512枚までメモリに持つ。超えたら「一番長く使われていない物」から捨てる(ディスクには残るので、また見えたらPNGから読む)。
- 実測テストで、600枚を作って、512枚を超えないこと・捨てた物は**再生成せず**にPNGから読み直すことを確認。

### 3.6 時間分割と優先順位(画面を止めない)
1枚を作るのに数ms〜十数msかかるので、全部を一度に作ると画面が止まります。**1フレームに使う時間枠(8ms)**の中で、順に処理します。
```cpp
while (!queue.empty()) {
    if (!first && 経過時間 >= 予算) break;   // 予算を使い切ったら次のフレームへ
    first = false;                            // ただし最低1件は進める(終わらなくなるのを防ぐ)
    処理する();
}
```
- **優先順位**: 画面に見えている項目(`Get()` が呼ばれた物)は、`deque` の**先頭に割り込ませる**。見えていない項目は、後ろに並べて、空いた時間に処理する。
- **重複の防止**: すでに予約した物は `unordered_set` で覚えておき、二重に予約しない。
- **失敗した項目**は覚えておき、再び試さない(毎フレーム失敗し続けるのを防ぐ)。
- **大きなファイル**(4MB超)は自動では作らない。街全体のFBX(約9MB)は、1枚で約4.6秒かかり、画面が止まったため。

### 3.7 ImGui(即時モード)で一覧を出す
- **画像の表示**: `ImGui::Image(ImTextureRef(srv), サイズ)`。ImGuiのDirectX11用の仕組みは、`ID3D11ShaderResourceView*` をそのまま画像の識別子として使える。
- **ListClipper**: 数百枚を毎フレームすべて処理しないよう、**見えている行だけ**を描く。見えている項目だけが `Get()` を呼ぶので、サムネイルの生成も「見えている物が優先」になる。
- **ドラッグ(回転)とホイール(ズーム)**: 画像の上に `InvisibleButton`(見えないボタン)を重ねて、`IsItemActive()`(押している間)と `MouseDelta`(マウスの移動量)を受け取る。
- ImGuiのパネルが開いている間は、マウスはパネルが受け取るので、ゲームの世界(建物の配置など)は反応しない(既存の `WantCaptureMouse` の仕組み)。

### 3.8 色空間(sRGBとリニア)— 今回の問題の中心
画面に出る色の値は、**ガンマ補正**(約2.2乗)されています。
```
sRGB = 255 × (リニア値)^(1/2.2)   に近い(正確には、下の変換式)
リニア値 → sRGB:   c <= 0.0031308 なら 12.92 × c、それ以外は 1.055 × c^(1/2.4) − 0.055
```
例: リニア 0.214 → sRGB 0.5(中くらいの明るさ)。**リニアの値をそのまま画面に出すと、暗く見える**のが今回の2つの問題の共通の原因でした。

| 場面 | 起きたこと |
|---|---|
| PNGをWICで読む | PNGの「sRGB」の印により、`_SRGB` 形式のテクスチャになった。`_SRGB` は読む時にsRGB→リニアに変換するので、**画面(UNORM)に直接出すと暗く**なった → `WIC_LOADER_IGNORE_SRGB` で生の値のまま読む |
| BlenderのMTLの `Kd` | `Kd` は**リニア空間の値**で書かれている。このエンジンは値をそのまま表示色にする(光の計算もsRGBのまま)ので、淡い青緑がほぼ黒に → Blender製のMTL(先頭に `# Blender MTL File`)だけ、`Kd` をsRGBに変換 |

> 学び: 「色の値は、どの色空間の値か」を意識する。画像ファイル・材質の値・画面(バックバッファ)のそれぞれで、リニアかsRGBかが違う。

### 3.9 モデルの周りを回るカメラ(球面座標)
```cpp
カメラ位置 = ( 距離 × sin(yaw) × cos(pitch),
              距離 × sin(pitch),
              距離 × cos(yaw) × cos(pitch) )     // 常に原点(モデルの中心)を見る
```
- `yaw`(横の角度)=0 で +Z 側(エンジンの前方側)から見る。π で -Z 側(背面)。
- `pitch` は ±1.5ラジアン(約86度)に収めて、真上・真下でカメラが回転できなくなるのを防ぐ。
- **フィット**: モデルの大きさ・原点の位置はバラバラなので、**中心を原点に移し、最大の辺が1.6になるよう拡縮**してから描く(`BuildController` の自動フィットと同じ考え方)。どんな素材も同じ大きさ・同じ位置で見える。

### 3.10 ファイルの探索(`std::filesystem`)
- `recursive_directory_iterator` でフォルダを再帰的に探す。`ModelLoaderRegistry::CanLoad`(拡張子)で、**読める形式だけ**を一覧に入れる(新しい形式のローダーを足せば、自動で一覧に出る)。
- パスは**プロジェクトからの相対パス**(区切りは `/`)だけ。提出先でも動くように、絶対パスは使わない。
- **重複の判定**: Kenneyのパックは、同じモデルが `OBJ format/x.obj`、`FBX format/x.fbx`、`GLB format/x.glb` に入っている。「パック+フォルダ(形式名のフォルダは区別しない)+名前」が同じ物を重複とし、OBJを優先して残す。
  最初の案は「同じパック+同じ名前」だったが、別フォルダの同名の別モデル(`Buildings/a.fbx` と `Props/a.fbx`)まで隠してしまうため、単体テストで気付いて直した。

### 3.11 設計の工夫
- **役割ごとに分ける**: 探す(`AssetCatalog`)・サムネイルを管理する(`ThumbnailCache`)・描く(`ModelPreviewRenderer`)・画面(`AssetBrowser`)。どれかを差し替えやすい。
- **使う側に負担をかけない**: パネルが閉じている間は `Update()` が即座に戻る(実測 約0.00003ms)。
- **RAII**: `Debug::ScopedInfoSuppress` は、スコープの間だけログを止め、抜けたら**自動で元に戻す**(`return` やエラーで途中で抜けても、戻し忘れない)。
- **失敗に備える**: モデルが読めない、PNGが壊れている、保存できない、のどの場合も、落ちずに続行する。

## 4. 見つけた問題と、その解決

| 問題 | 原因 | 解決 |
|---|---|---|
| 2回目の起動で、サムネイルが暗い | WICがPNGを `_SRGB` 形式で読んだ(3.8) | `WIC_LOADER_IGNORE_SRGB`。単体テストで形式を確認 |
| Quaterniusの `_Mat` モデルが真っ暗 | BlenderのMTLの `Kd` がリニアの値(3.8) | Blender製MTLだけ、`Kd` をsRGBに変換。サムネイルの版を2に |
| 別フォルダの同名モデルが隠れる | 重複判定が粗かった(3.10) | 「形式名のフォルダ違い、または同じフォルダ」だけを重複に |
| 街全体のFBXで、画面が約4.6秒止まる | 巨大ファイル | 4MB超はクリックした時だけ作る |
| ログが「読み込んだ」で埋まる | 大量のモデルを読む時の `Info` ログ | `ScopedInfoSuppress` |
| HUDが出ると3Dが「カリングなし」になっていた | `UIRenderer` が状態を変えて、元に戻さなかった | `Renderer` が毎フレームと各モデル描画の前に、自分で設定する(3.1の学び) |
| テストの初期化で `small` が型名に化けた | Windowsのヘッダーが `#define small char` を定義している | 変数名を変える(`reduced`)。`min`/`max` と同じ種類の「Windowsのマクロ」の罠 |

**「測ってから直す」の効果**: 最長の生成時間を記録する仕組みを足したら、1つのファイルだけが突出して重いことが数字で分かり、的確に直せました(カリングの時も、描画時の設定を読み取って、原因を確認してから直した)。

## 5. 検証のしかた(テストの考え方)

- **単体テスト(スクラッチ)**: 一覧の作成、キー、縮小、PNGの往復(書いて読んで、全画素が一致)、キャッシュの動作(初回・2回目・更新・壊れたPNG・失敗・一時停止・優先順・上限・大きなファイル)。
- **スタブ(代用品)**: 本物の `Renderer` はウィンドウが要るので、テストでは「デバイスとコンテキストだけを持つ代用品」と、「モデルを描く代わりに単色で塗る代用品」を使った。**画面を出さずに(WARPという、ソフトウェアのGPUで)**テストできる。
- **本番の動作確認**: 一時的な診断コード(自動でパネルを開き、画面を保存し、時間を記録する)を入れて実際のゲームを動かし、確認後に**削除**した。
- **数字で確認**: 初回は707枚を約6〜7秒、2回目は約21フレーム、閉じている間は実質ゼロ。
- **回帰の確認**: 他に影響が出ていないことを、画面を保存して比べた(カリングを変えた時は、修正前後の画像を比べた)。

## 6. 次に似たものを作る時のチェックリスト

1. **重い処理は、1回だけ**にして結果を保存できないか?(キャッシュ。キーは「元データの変化」で決まる物にする)
2. 保存した物が**古くなる条件**は何か?(元のファイルの変化、見た目の仕様の変更 → 版の数字)
3. 重い処理を**時間枠で分割**できるか?最低1件は進めるか?見えている物を優先しているか?
4. 巨大な入力(想定外に大きいファイル)で、**画面が止まらないか**?
5. 描画の状態(描画先・ビューポート・光・カリングなど)を**変えたら、元に戻す**か、使う側が毎回設定しているか?
6. **色の値はどの色空間か**?画像・材質・画面で、リニアかsRGBかを確認したか?
7. 失敗(読めない・壊れている・保存できない)で**落ちない**か?失敗を何度も繰り返さないか?
8. 閉じている/使っていない時の**負荷はゼロ**か?
9. 実測した数字を記録したか?(平均・最長・件数)
