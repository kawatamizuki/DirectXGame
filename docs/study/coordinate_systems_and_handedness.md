## 1. 何が起きたか(症状)

SimplePoly City の建物をプレビューで描いたら、看板の文字が鏡に映したように反転していました。

- 「Bakery」→ 左右が逆になった文字
- 「BOOKS」「PIZZA」も同様

それまで気付かなかった理由は、Kenney の建物が**ほぼ左右対称**で、鏡像になっても見た目で分からなかったからです。つまり、**ずっと前から全モデルが鏡像で表示されていた**のを、文字入りのモデルで初めて発見した、ということです。

> 教訓: 鏡像のバグは、左右対称の物では見つからない。文字(非対称な物)で初めて見える。

## 2. 用語の整理

| 用語 | 意味 |
|---|---|
| 座標系 | 位置を数字(x, y, z)で表すための「ものさしの向きの決め方」。どの方向が右・上・前かを決める |
| 軸(X軸・Y軸・Z軸) | 3つの方向。x=右、y=上、z=奥行き、と割り当てるのが多い |
| 右手系(right-handed) | 右手の親指=X、人差し指=Y、中指=Z としたときの向きの決め方。画面の手前向きが +Z |
| 左手系(left-handed) | 左手で同じことをした向き。画面の奥向きが +Z |
| 利き手(handedness) | 右手系か左手系か、という性質のこと |
| Y-up / Z-up | 「上」がどの軸か。Y-up は Y が上、Z-up は Z が上(Blender など) |
| 前方(forward) | モデルや人が向いている方向 |
| 巻き順(winding order) | 三角形の3頂点をどの順に並べたか。画面上で時計回りか反時計回りか |
| 表(front face) / 裏(back face) | 三角形を見て、巻き順が決められた向きなら表、逆なら裏 |
| カリング(culling) | 裏向きの三角形を描かずに捨てる処理。高速化のため |
| 法線(normal) | 面に垂直で、面の向きを表すベクトル。光の当たり方の計算に使う |
| 外積(cross product) | 2つのベクトルに垂直なベクトルを作る計算。面の向きを求めるのに使う |
| 行列式(determinant) | 行列が空間を「反転させるか」を表す数。負なら鏡像(向きが裏返る) |
| 鏡像変換(reflection) | ある軸の符号を反転して、鏡に映した形にする変換。行列式が -1 になる |
| UV座標 | テクスチャ(画像)のどの位置を貼るかを表す2次元の座標 |
| ワールド・ビュー・プロジェクション | 3D 描画の座標変換の段階(後述) |

## 3. 右手系と左手系(一番大事な部分)

### 3.1 2つの系の違い

X を右、Y を上に固定したとき、**Z をどちら向きにするか**で2種類に分かれます。

```
        Y(上)                         Y(上)
        |                             |
        |                             |
        |______ X(右)                 |______ X(右)
       /                               \
      /                                 \
     Z(手前: 画面から飛び出す)           Z(奥: 画面の奥へ進む)

      右手系(RH)                        左手系(LH)
   OpenGL, Blender(Y-up書き出し)         Direct3D(この作品), Unity
   glTF, Maya, OBJ/FBX の多く
```

- **右手系**: Z が自分(見ている人)の方へ向かってくる。カメラは -Z 方向を見る。
- **左手系**: Z が画面の奥へ向かう。カメラは +Z 方向を見る。このゲームの「前方 = +Z」はこれ。

### 3.2 どちらが「正しい」のか
どちらも正しく、**ただの約束事**です。問題は、**約束が違うデータをそのまま混ぜると鏡像になる**ことです。

主なソフトの約束:

| ソフト・形式 | 利き手 | 上 | 備考 |
|---|---|---|---|
| Direct3D / DirectXMath(この作品の描画) | 左手系(LH関数を使う場合) | Y | `XMMatrixLookAtLH` などは「LH」付きの関数 |
| Unity | 左手系 | Y | |
| Unreal Engine | 左手系 | Z | |
| OpenGL | 右手系 | Y | カメラは -Z を見る |
| Blender | 右手系 | Z | OBJ/FBX 書き出しの設定で Y-up にできる |
| glTF | 右手系 | Y | モデルの正面は +Z |
| OBJ | 決まりは無いが、ほぼ右手系・Y-up | Y | Blender の標準書き出しは「前方 = -Z、上 = Y」 |
| FBX | ファイルの中に軸の設定が書いてある | 作り手による | ufbx が読み取って変換できる |

### 3.3 同じ数字でも、見る側の系が違うと鏡像になる
例えば、モデルの頂点が `(1, 0, 0)` にある「右の端の点」だとします。

- 右手系のデータを**右手系で**見る → 右に見える(正しい)
- 右手系のデータを**左手系の画面で**見る → 数字は同じでも、Z の向きが逆の世界なので、**全体が左右(または前後)に反転して**見える

3D の形は、**1つの軸の向きを反転させた鏡像**になります。看板の文字のような「非対称な物」は、鏡文字になって見つかります。

## 4. なぜ今回の問題が起きたか(このプロジェクトの場合)

### 4.1 描画は左手系
`Graphics/Camera.cpp`:
```cpp
return XMMatrixLookAtLH(eye, target, up);       // カメラの行列(LH = 左手系)
return XMMatrixPerspectiveFovLH(...);           // 透視投影(LH)
```
`LH` が付く関数を使っているので、このゲームの 3D 空間は**左手系**です(前方が +Z)。

### 4.2 モデルのデータは右手系
OBJ(Kenney)も FBX(SimplePoly)も、Blender や Maya などの**右手系**で作られています。読み込みコードは、頂点の数字をそのまま `Vertex` に入れていました(`ObjLoader`)。

### 4.3 組み合わせた結果
```
右手系で作られた頂点の数字  →  そのまま  →  左手系の画面で表示  =  鏡像
```

### 4.4 なぜ今まで表示が壊れなかったのか(重要)
モデルは鏡像でも、**面の裏表(カリング)は壊れていませんでした**。理由:

- Direct3D の既定は「**時計回りの三角形が表**」。
- 右手系のデータは「反時計回りが表」で作られているが、**左手系の画面で見ると時計回りに見える**。
- 結果として、裏表の判定は偶然ちょうど合う(鏡像の副作用)。

つまり、**形は鏡像なのに、壊れて見えない**という、見つけにくい状態でした。

> 補足(調査中に分かったこと、2026-10-21 に修正済み): `UIRenderer` が描画時にカリング無し(`CULL_NONE`)の設定にして、元に戻していませんでした。実際に、HUD が出るゲームシーンでは2フレーム目以降の3D描画がカリング無しになっていたことを、描画時の設定を読み取って確認しました。`Renderer` が自分のラスタライザ状態(背面カリング)を毎フレームと各モデル描画の前に設定するよう直しました(`Graphics/Renderer.cpp`)。

## 5. 解決方法の選択肢と、選んだ方法

| 方法 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. 読み込み時にデータを変換する(採用)** | 頂点の Z を反転し、巻き順も直す | 全モデルが正しい形になる。描画側は一切変えない。毎フレームの負担なし | 向きが変わる(後述) |
| B. 描画側で鏡像を打ち消す | カメラの行列に X や Z の反転を入れる | データはそのまま | 全部の描画(UI・デバッグ線・地面)に影響。カリングも反転が必要。複雑 |
| C. 描画を右手系にする | `XMMatrixLookAtRH` などに切り替える | 素材と同じ系になる | エンジン全体(カメラ・道路・建物の向きの計算)を右手系に作り直す必要がある |
| D. 建物ごとに向きだけ補正する | モデルごとに180度回すなど | 小さい | 鏡像は直らない(文字は鏡文字のまま) |

**A を選んだ理由**: 変換が「読み込み時の1回」で済み、後ろの描画・配置・当たり判定が全て影響を受けません。データの入口で系を揃える、というのは、実際のゲームエンジンでもよく使う設計です(「インポート時にエンジンの座標系へ変換する」)。

### 5.1 どの軸を反転するか(X か Z か)
鏡像を直すだけなら、X を反転しても Z を反転しても同じです(どちらも1軸の反転)。違いは**モデルの前方がどちらを向くか**だけです。

- **Z を反転**: 右手系の「前方 = -Z」が、エンジンの「前方 = +Z」になる。→ **採用**
- X を反転: 前方は -Z のまま変わらない。

エンジンは「前方 = +Z」(建物の向きの計算など)を前提にしているので、Z を反転して**作者が決めた前方が、エンジンの前方に自然に重なる**ようにしました。

その結果、Kenney の建物は扉の向きが180度反転して見えるようになりました(位置は同じ)。

## 6. 実際に書いたコードの解説

### 6.1 変換の本体(`Graphics/ModelData.h`)
```cpp
void ConvertFromRightHanded()
{
    // ① 全頂点の Z と、法線の Z を反転する
    for (Vertex& v : vertices)
    {
        v.z  = -v.z;
        v.nz = -v.nz;
    }
    // ② 三角形ごとに、2番目と3番目の頂点を入れ替える(巻き順を直す)
    for (size_t i = 0; i + 2 < vertices.size(); i += 3)
    {
        std::swap(vertices[i + 1], vertices[i + 2]);
    }
    // ③ バウンディングボックスの Z も反転(大小が入れ替わるので min/max を入れ替える)
    float newMinZ = -boundsMax.z;
    float newMaxZ = -boundsMin.z;
    boundsMin.z = newMinZ;
    boundsMax.z = newMaxZ;
}
```

**①位置と法線の Z を反転**
- 鏡に映す操作そのものです。`(x, y, z)` → `(x, y, -z)`。
- 法線も同じ向きに映す必要があります(法線は面の向きを表すので、鏡に映した面は法線も映る)。

**②2番目と3番目の頂点を入れ替える**
- 鏡に映すと、三角形の**巻き順(時計回り/反時計回り)が逆になります**。入れ替えないと、表と裏が逆になり、裏側だけが描かれる(カリングが有効な場合)。
- 3つの頂点 A, B, C を A, C, B にすると、巻き順が逆になり、表に戻ります。
- UV は頂点にくっついているので、頂点ごと入れ替えるだけで正しく追従します(UV 自体は変えない)。

**③バウンディングボックス**
- `BuildController` が建物をマスに合わせて拡縮・配置する時に使う値です。
- 例: Z の範囲が `3〜9` のとき、反転すると `-9〜-3`。**小さい方が min になるよう**入れ替えます(`min = -oldMax`, `max = -oldMin`)。

### 6.2 どこで呼ぶか
- `Graphics/ObjModelLoader.cpp`: OBJ を読んだ後。
- `Graphics/FbxModelLoader.cpp`: FBX を読んだ後(ufbx で右手系・Y上に揃えた後)。

```cpp
// 例: ObjModelLoader.cpp
out.ConvertFromRightHanded();
return true;
```
**ローダーが1回だけ呼ぶ**ルールです(2回呼ぶと元に戻ってしまう。テストで「2回で元に戻る」ことを確認)。

読み込み後のデータは `ModelData` に入っていて、`ModelData` の定義の説明に「エンジンの座標系(左手系)で持つ」と書いてあります。**データ型の約束を決めて、入口(ローダー)で守らせる**設計です。

### 6.3 呼び出しの全体の流れ
```
Model::LoadFromFile(path)
  └ ModelLoaderRegistry が拡張子でローダーを選ぶ
      ├ ObjModelLoader … OBJを読む → ConvertFromRightHanded()
      └ FbxModelLoader … ufbxで読む → 右手系Y上にそろえる → ConvertFromRightHanded()
  ↓ どちらも「エンジンの左手系」のModelDataを返す
Model::CreateFromModelData(data)  … 頂点バッファとテクスチャを作る
```
**形式が増えても、描画側は座標系を気にしなくてよい**構造です。

## 7. 数学的な裏付け(なぜ頂点の順を入れ替えるのか)

### 7.1 Z の反転を行列で書く
```
      | 1  0  0 |
M  =  | 0  1  0 |      det(M) = -1   ← 行列式が負 = 鏡像
      | 0  0 -1 |
```
行列式が **-1**(負)なのが、「鏡像(向きが裏返る)」の証拠です。回転の行列式は +1、拡大縮小は正の数。**負になるのは反転だけ**。

### 7.2 三角形の「表」を表す式
三角形の頂点を v0, v1, v2 とすると、外積:
```
n_geo = (v1 - v0) × (v2 - v0)
```
の向きが、三角形の「面の向き」になります。**この式の向きが、保存されている法線と同じ向きなら、巻き順が正しい**と言えます。

### 7.3 反転すると何が起きるか
線形変換 A に対して、次の関係が成り立ちます。
```
(A u) × (A v) = det(A) · A⁻ᵀ (u × v)
```
M(Z反転)では `det(M) = -1`、M⁻ᵀ = M なので:
```
(M u) × (M v) = - M (u × v)
```
- 反転後の三角形の外積は、「**反転した法線と逆向き**」になる(= 巻き順が逆になった)。
- 2番目と3番目の頂点を入れ替えると、外積の符号が反転して、`+M n` に戻る(= 反転した法線と同じ向き)。**これが入れ替えの理由です。**

### 7.4 数値例
元の三角形(右手系、法線は +Z):
```
v0 = (0,0,0)  v1 = (1,0,0)  v2 = (0,1,0)
n_geo = (1,0,0) × (0,1,0) = (0,0,1)      ← 法線 +Z と同じ向き ✓
```
Z を反転しても、この三角形は z=0 の平面なので位置は変わらないが、法線は `(0,0,-1)` になる。
入れ替えなしの外積: `(1,0,0) × (0,1,0) = (0,0,1)` → 反転後の法線 `(0,0,-1)` と**逆向き ✗**
入れ替え後 (v0, v2, v1): `(0,1,0) × (1,0,0) = (0,0,-1)` → **一致 ✓**

### 7.5 左手系での「表」
左手系で、画面に向かって見えている三角形が**時計回り**に並ぶのと、外積が外向きの法線と一致するのは同じ条件です(右手系の画面では反時計回りになる)。
Direct3D の既定は「時計回りが表」なので、**外積が法線と一致していれば、既定のカリングで表として描かれる**。テストで使った判定は、この性質に基づいています。

## 8. ufbx(FBXライブラリ)が関係する部分

`Graphics/FbxModelLoader.cpp`:
```cpp
ufbx_load_opts opts = {};
opts.target_axes = ufbx_axes_right_handed_y_up; // 右手系・Y上に揃える
opts.target_unit_meters = 1.0f;                 // 単位をメートルに揃える
opts.generate_missing_normals = true;           // 法線が無いモデルは作る
```
- FBX はファイルの中に「この作品の上方向は Z、単位は cm」のような**軸と単位の設定が書いてある**。作る元のソフトによって違う(Max は Z-up、Maya は Y-up など)。
- ufbx はそれを読み取って、指定した軸(`target_axes`)に**自動で変換**してくれる。ここでは「右手系・Y上」にそろえる。
- そのあとで、自前の `ConvertFromRightHanded()` が**エンジンの左手系**に変換する。

つまり、2段階です。
```
任意のFBXの軸設定 → [ufbx] → 右手系・Y上・メートル → [ConvertFromRightHanded] → エンジンの左手系
```

### 8.1 ノードの変換が鏡像の場合
FBX の中のノード(部品)に、**負のスケール**(-1 など)が付いている場合があります(左右対称の部品を鏡像でコピーした物など)。
```cpp
const bool flipWinding = ufbx_matrix_determinant(&toWorld) < 0.0;
...
if (flipWinding) std::swap(corners[1], corners[2]);
```
行列式が負 = 鏡像なので、7章と同じ理由で巻き順を直しています。**同じ原理の別の場面**です。

### 8.2 UV の上下反転
```cpp
vertex.v = 1.0f - static_cast<float>(uv.y);
```
OBJ・FBX・OpenGL のテクスチャの原点は**左下**、Direct3D は**左上**です。そのため、V を `1 - v` にします。これは座標系(左手/右手)とは**別の話**ですが、読み込み時に揃える点が同じです。OBJ ローダーにも同じ処理があります。

### 8.3 「front(前面)は forward(前方)の反対」
ufbx のヘッダーに `NOTE: front is the opposite from forward!` とあります。ufbx の `front` 軸は「見ている人の方を向く軸」で、モデルが向いている「前方」とは逆、という意味です。
`ufbx_axes_right_handed_y_up` は `front = +Z` なので、前方は -Z になる、はずでした。

## 9. どうやって確認したか

| 確認 | 内容 |
|---|---|
| 値のテスト | 3頂点の三角形を変換して、Z・法線・頂点の順・UV・境界が期待どおりか、厳密に比較。2回変換すると元に戻ることも確認 |
| 面の向きのテスト | 実モデルで、「外積が頂点法線と同じ向きの三角形の割合」を計算。99.7〜100% なら巻き順が正しい |
| 目視 | SimplePoly の建物を描いて、看板の文字が正しい向きで読めること(「Bakery」「BOOKS」「PIZZA」「Fruits Corner」)を確認 |
| 回帰 | OBJ(Kenney)も同じ関数を通って、同様に正しいこと。ゲーム本体の Debug/Release を起動し、建物が地面に付いていることを確認 |
| 負荷 | 変換の時間を計測: 2万頂点で約0.025ms、100万頂点で約7.5ms。読み込み時の1回だけで、描画の毎フレームの負担はなし |

**鏡像を見つけるコツ**: 文字・矢印・ロゴなど、**非対称な物**を表示して確かめる。左右対称の物では気付けない。

## 10. 新しい素材を入れる時のチェックリスト

1. **モデルを描いてみて、文字があるものは文字が正しく読めるか**を確認する。
2. **正面の向き**を確認する(扉がどちらを向くか)。パックによって違う。
3. **大きさ(単位)**は `BuildController` の自動フィットで揃うが、**原点の位置**が変でも自動で補正されるかを見る。
4. **テクスチャが貼られているか**(貼られていなければ、探し方の規則を確認)。
5. **色が変**(真っ黒など)なら、法線の向きが逆の可能性がある(巻き順・法線の変換を疑う)。
6. 新しい**形式のローダーを足す**時は、右手系のデータなら `ConvertFromRightHanded()` を呼ぶ。左手系のデータ(Unity で作った素材など)なら**呼ばない**。
7. テストモデルを1つ用意して(Zだけが見分けられる、非対称な形に文字を入れた箱)、変換前後で見比べると確実。

## 11. まだ残っている注意点

- **モデルの正面の向きがパックで違う**: 変換後、Kenney の建物は正面が +Z、SimplePoly の建物は正面が -Z。SimplePoly を使う時に、建物の定義へ**向きの補正値(180度)**を足す(バックログ)。
  なぜ SimplePoly だけ逆なのかは未調査(FBX が宣言する軸と、実際のモデルの正面が食い違っている可能性がある)。
- **保存済みのマップ**: 建物の位置は変わらないが、扉の向きが180度反転して見える。
- **カリング設定**: `Renderer` が自分で設定していない問題(4.4)。

## 12. 用語集(追加)

| 用語 | 意味 |
|---|---|
| ベクトル | 向きと大きさを持つ量。(x, y, z) の3つの数で表す |
| 内積(dot) | 2つのベクトルが同じ向きかを表す数。同じ向きなら正、逆なら負、直角なら0 |
| 行列 | 回転・拡大縮小・移動などの変換を、まとめて表した数の表 |
| 線形変換 | 原点を動かさない変換(回転・拡縮・反転)。行列で表せる |
| ワールド空間 | ゲームの世界全体の座標 |
| ローカル空間(モデル空間) | モデル自身の中心などを基準にした座標 |
| ビュー空間 | カメラを基準にした座標 |
| 行ベクトル方式 | DirectXMath は `v. = v × M` と、ベクトルを横に書く方式。HLSL に渡す前に行列を転置しているのも、この方式の違いによる |
| インポート | 外部のファイルを読み込んで、エンジンの形に変換すること |
| 頂点バッファ | GPU に渡す頂点のデータ |
| テクスチャ座標(UV) | 画像のどこを貼るか。U=横、V=縦 |
| バウンディングボックス(AABB) | モデルを囲む、軸に平行な箱。大きさの計測・当たり判定の目安 |
| ロード時変換 | データを読み込む時に1回だけ、エンジンの形に変換する設計。後ろの処理(描画・配置)が形式の違いを気にしなくてよくなる |
