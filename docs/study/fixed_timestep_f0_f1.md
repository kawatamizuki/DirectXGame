# 学習メモ: 固定時間刻み(F0・F1)と、時間の進め方の選び方

## 1. 何をしたか
- F0: 時間の進め方を変える前の、シミュレーションの結果(指紋)を記録した(`docs/design/fixed_timestep.md`)。
- F1: 固定刻みの部品 `Core/FixedTimestep.h` と、時計の `GameClock::Advance` を作った。単体テストつき。ゲームの動きは、まだ変えていない。

## 2. 用語
| 用語 | 意味 |
|---|---|
| dt(デルタタイム) | 前の更新から経った時間 |
| 可変dt | 毎フレーム、実際に経った時間で更新する方式 |
| 固定刻み(固定タイムステップ) | 1回の更新で進める時間を、いつも同じにする方式 |
| アキュムレーター | 経った時間を貯めておき、固定刻みの分だけ取り出して更新する仕組み |
| 死のスパイラル | 更新が重くて遅れる → 追いつこうと回数を増やす → さらに重くなる、の悪循環 |
| 補間 | 前のステップと今のステップの間の位置を、割合で計算して描くこと(見た目だけ) |
| 決定論 | 同じ条件なら、必ず同じ結果になる性質 |

## 3. 技術の選定(7項目)
### 3.1 解決したい問題と要求条件
- 問題: 今は1フレームに1回、「実時間 × 倍率」だけ進めている。FPS・倍率で1回の長さが変わり、住民の結果が変わる(F0: 同じ26週で、外出の抽選が倍率1で1315回、倍率20で1174回)。
- 要求: ① FPS・倍率が違っても、同じゲーム内時間なら同じ結果 ② 倍率は回数だけを変える ③ 自動検証は、通常プレイと同じ更新を、描画を省いて速く回す ④ 低FPS・長い停止でも、壊れない・重くなりすぎない ⑤ 既存のゲームの遊び心地(1倍・60FPS)を、なるべく変えない。

### 3.2 候補と、3.3 メリット・デメリット
| 方式 | 中身 | メリット | デメリット |
|---|---|---|---|
| A. 可変dt(今の方式) | 1フレーム1回、実時間×倍率で進める | いちばん簡単。描画となめらかに合う | FPS・倍率で結果が変わる(要求①②を満たさない)。長い停止で一気に進む |
| B. 可変dt+上限・分割 | dt に上限を付け、大きい時は細かく分けて進める | 長い停止に強い。変更が小さい | 分け方がFPSで変わるので、結果はやはりFPS・倍率で変わる |
| C. フレーム固定(1フレーム=1回) | 実時間に関係なく、1フレームで決まった時間だけ進める(今の「再現」の方式) | 決定論。簡単 | FPSが下がると、ゲームの時間も遅くなる(30FPSなら半分の速さ)。普段のプレイに向かない |
| D. 固定刻み+アキュムレーター | 実時間×倍率を貯め、固定刻みの分だけ回す(Unity の FixedUpdate) | 決定論(要求①②)。描画と独立。回すだけなので高速化しやすい(要求③) | 高FPSで動きがカクつくことがある(→補間)。上限が無いと死のスパイラル |
| E. Dに描画の補間を足す | Dに加えて、描画の時に前後のステップを補間 | Dの長所+見た目がなめらか | 前の位置を持つ必要があり、描画側の変更が増える |
| F. 独立した更新スレッド | シミュレーション専用のスレッドで、固定刻みで回す | 描画が重くても、シミュレーションが止まらない。マルチコアを使える | 描画・UI・入力と、データの共有(排他・コピー)が必要。不具合を探しにくく、決定論も崩しやすい |

### 3.4 採用した方式と理由
**D(固定刻み+アキュムレーター)を採用し、見た目が気になればE(補間)を後から足す。**
- 要求①②を、仕組みで満たす(1回の刻みが、FPS・倍率に関係なく同じ)。
- 要求③: 自動検証は「同じステップを、描画せずに多く回す」だけになる。
- 要求④: 1フレームの実時間と回数に上限を付けて、死のスパイラルを防ぐ(超えた分は遅くなるだけ。刻みは変えないので、決定論は崩れない)。
- 要求⑤: 刻みを「1倍・60FPSの今の1フレーム」と同じ 1/60秒 にするので、普段の遊び心地は、ほぼ変わらない。
- 実測で、1回の更新が十分に軽い(下の3.6)。1フレームに数回まわしても、問題にならない。

### 3.5 他の方式を採用しなかった理由
- A・B: FPS・倍率で結果が変わる問題が残る(要求①②を満たさない)。
- C: FPSが下がると、ゲームの時間まで遅くなる。検証には使えるが、普段のプレイには向かない。
- E: 今の60FPSと同じ見え方になるだけなので、急がない。描画側の変更が増えるので、必要になってから足す(F6)。
- F: このゲームの更新は、とても軽い(1回0.003ms)。スレッドにする利点が小さく、排他・決定論の難しさに見合わない。

### 3.6 根拠と、まだ確認できていない点
- 実測(住民18人、4週、1/60秒刻み): 26,202 ステップ = Debug 81ms(1回0.0031ms)/ Release 7.7ms。4倍・30FPSでも1フレーム8回 = 約0.025ms(Debug)。
- コード: 乱数は `DemandSystem` の1本だけで、描画・UIから引かない → 同じ回数のステップなら同じ結果(3-Cの指紋の一致でも確認済み)。週の区切りは、時計が区切りで分けて数えているので、刻みに左右されない。
- 単体テスト: 30/60/120FPS・ばらつく間隔で、同じ回数・同じ時計の状態。`Update(dt)` と `Advance(dt×倍率)` は、2万回、全ての値が一致。
- まだ確認できていない: 実際のゲームに組み込んだ時の指紋(F2・F3の後、F0の倍率1の指紋と一致するか)/ 大きな街(数百人)での重さ / 高FPSでの見た目のカクつき / Debug版とRelease版の間で、結果が一致するか(最適化で小数の計算がわずかに違う可能性。保証の範囲外としている)。

### 3.7 見直す条件
- 住民が増えて、1回の更新が重くなり、1フレームに回しきれなくなった(上限で遅くなるのが目立つ) → 刻みを長くする(1/30秒)・処理の軽量化・F(スレッド)を検討。
- 高FPSでのカクつきが気になる → E(補間)を足す。
- ネットワーク対戦など、別のPCと結果を合わせる必要が出た → 小数の計算の一致(固定小数点・決まった計算順)まで考える必要がある。

## 4. 作った物の要点
### FixedTimestep(アキュムレーター)
```cpp
m_accumulator += realDeltaSeconds * timeScale;                 // 実時間×倍率を貯める
double count = std::floor(m_accumulator / step + 1e-9);         // 刻みが何回分あるか
if (count > maxStepsPerFrame) { /* 超えた分は捨てる(遅くなるだけ) */ }
m_accumulator -= count * step;                                  // 使った分を引く(端数は次のフレームへ)
```
- 端数を**捨てずに次へ持ち越す**ので、長い時間で見ても、回数がずれない(今の3秒タイマーは端数を捨てていて、これが倍率で結果が変わる原因の1つ)。
- 貯まりは `double`。`float` で長時間足し続けると、誤差がたまるため。
- `+1e-9`: 割り算の丸めで、ちょうど1回分なのに0回になるのを防ぐ。

### GameClock::Advance
- `Update(dt)` は、中で `Advance(dt × 倍率)` を呼ぶだけにした。計算の中身は動かしていないので、今のゲームの動きは変わらない。

## 5. 気をつけること
- 新しい「時間で進む処理」を足す時は、1ステップの関数の中で、ステップの刻みで進める(フレームの dt を直接使わない)。
- 見た目だけの物(昼夜の光・カメラ・UIのアニメーション・音)は、今までどおり、フレームの実時間で動かしてよい。
- 1フレームの上限で捨てた時間は、「遅くなった」だけ。結果の決定論は崩れない。
