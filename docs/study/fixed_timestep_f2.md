# 学習メモ: 通常プレイを固定時間刻みに切り替える(F2)

## 1. 何をしたか
通常プレイ(ゲームシーンの Playing)の時計と住民の更新を、「1フレームに1回、実時間×倍率」から「固定刻み(ゲーム内 1/60秒)を、貯まった回数だけ」に変えた。F1で作った `FixedTimestep` を、ゲーム本体で使い始めた。
変えたのは `Core/Game.{h,cpp}` だけ。住民AIのルール・3秒周期・再現・巻き戻し・耐久試験・自動検証は、変えていない。

## 2. 実装の要点
```cpp
// フレームの最初: 固定刻みの時は、ここで時計を進めない。使っていない間は、貯まりを捨てる。
const bool fixedSim = UsesFixedSimulation();   // Playing で、再現・巻き戻し・耐久試験が動いていない
if (!fixedSim) { m_fixedStep.Reset(); m_gameClock.Update(clockDelta); }

// 住民を更新していた所:
int Game::UpdateSimulationFixed(float realDeltaSeconds)
{
    const int steps = m_fixedStep.Accumulate(realDeltaSeconds, m_gameClock.GetTimeScale());
    if (steps == 0 && 倍率が0) { 進める時間0で住民の更新を1回(今までどおり); return 0; }
    return RunSimulationSteps(steps);       // 時計 Advance(1/60) → 住民 Update を steps 回
}
```
- 1ステップの中は「時計 → 住民」。耐久試験・自動検証と同じ順番にした(F3でそろえやすい)。
- 住民デバッグの「一時停止の条件」に当たったら、そのステップで止める。1フレームに何回も回している時に、止まるべき所を通り過ぎないため。
- 街の読み込み(`SetOnWorldReplaced`)で、貯まりを捨てる。

## 3. 技術の選定(F2で決めたこと)
### 3.1 問題と要求
固定刻みを、普段のプレイに入れる。ただし、① 再現・巻き戻し・耐久試験を壊さない ② 一時停止・編集モード・読み込みで、おかしな動き(まとめて進む・余分に進む)をしない ③ 1倍の結果(F0)を変えない。

### 3.2 候補・3.3 長所と短所・3.4 採用・3.5 不採用の理由
| 決めたこと | 候補 | 採用 | 理由 |
|---|---|---|---|
| どこから切り替えるか | (a) 全ての経路(通常・再現・巻き戻し・耐久試験・自動検証)を一度に / (b) 通常プレイだけ先に | (b) | 一度に変えると、どこで結果が変わったか分からない。(b)なら、F0の倍率1と比べて、通常プレイだけを確かめられる。再現は記録を「フレーム番号」で持っていて、直す量が多い(F3) |
| 時計を進める場所 | (a) フレームの最初に1回(今まで) / (b) ステップの中で、住民の直前 | (b) | 時計と住民を、同じ刻みで、同じ順番に進めるため。(a)だと、1フレームに複数回まわす時、時計と住民の時間がずれる |
| 一時停止中の住民の更新 | (a) 何も呼ばない / (b) 進める時間0の更新を、毎フレーム呼ぶ(今まで) / (c) 一時停止中だけ(b) | (c) | (a)は、止めている間に出した行動テストの指示(帰宅など)が、効かなくなる。(b)は、動いている時もFPSで呼ぶ回数が変わり、結果がずれるおそれ。(c)は、今の操作感を保ち、動いている時の決定論も守る |
| 貯まった時間の扱い | (a) いつも持ち越す / (b) 固定刻みを使わないフレーム・読み込みで捨てる | (b) | (a)は、編集モードから戻った時や、読み込んだ直後に、前の時間でまとめて進んでしまう。捨てても、1ステップ未満の時間なので、遊びに影響しない |

### 3.6 根拠と、まだ確認できていない点
- F0の倍率1と、ステップ数・指紋が4つとも完全に一致(2つの街 × 2つの種、26週)。
- 30/60/120/144FPS・ばらつくFPS × 1/2/4倍の22通りで、同じステップ数なら指紋が一致。ゲーム内の速さはちょうど1/2/4倍。
- 一時停止・編集モード・読み込みを挟んでも、20000ステップ後の指紋が一致。読み込みで貯まりが0になる。
- まだ: 実機での手触り(歩きの見た目・倍速の感じ)/ 再現・巻き戻し・耐久試験は、まだ古い進め方(F3)/ 住民が多い街での、低FPS時の重さ。

### 3.7 見直す条件
- 再現・巻き戻しも固定刻みにそろえたら(F3)、`UsesFixedSimulation` の条件を減らせる。
- 一時停止中の「進める時間0の更新」に頼る処理が増えたら、「止まっている間だけの処理」として、住民の更新から分けることを考える。

## 4. 低FPSでの遅れ(上限0.25秒)
- 1フレームが0.25秒以下(4FPS以上)なら、遅れない。それより長いと、ゲーム内の速さ = 0.25 ÷ フレームの秒数 × 倍率(2FPSで半分)。
- 遅れても、結果は同じステップ数のものと同じ(決定論は崩れない)。
- 回数の上限(240回)は、今の最大4倍では効かない(4倍・0.25秒で60回)。

## 5. 勉強するとよいテーマ(ChatGPTの学習チャット向け)
- ゲームループの構造(入力 → 更新 → 描画)と、更新と描画を分ける理由

- フレームペーシング(垂直同期・FPS上限)と、時間の測り方

## 6. 追加検証で学んだこと(2026-11-14)
### 6.1 リスクを、コードから洗い出す
F2のコードを読み直して、「壊れるとしたら、どこか」を先に並べてから、それぞれを確かめる診断を作った。
| リスク | 確かめ方 |
|---|---|
| 速度を変えた時、前の速度で貯まった端数が混ざる | 速度とフレーム間隔を、フレームごとにでたらめに変える |
| 一時停止中の「進める時間0の更新」が、住民の状態によっては何かを変える | 自宅・移動中・利用中・帰宅中の全てを含む時点で、何十回も止める |
| 1フレームに何回も回す時、止まるべき所を通り過ぎる | 4倍・30FPSで「到着」で止め、60FPS・1倍と同じステップか |
| セーブ→ロードで、保存していない状態が失われる | 住民の状態が違う10か所で、セーブ→ロードして続けた街を、そのまま続けた街と比べる |
| 実際の dt は float で、1/60 から少しずれる | float の 1/60 を1時間分(216000回)回す |

### 6.2 診断そのものの誤りに気をつける
- 1回目の診断では、「止まったステップ数」が1倍と4倍で違って見えた。原因は、診断が「出した回数」(`TotalSteps`。途中で止めた分も数える)を数えていたこと。実際に回した回数(`UpdateSimulationFixed` の戻り値)で数え直すと、同じだった。
- 「最初にずれるステップを探す」診断が、無限ループで止まらなくなった。原因は、既知の丸め(`visitHoursLeft`)の違いだけで「読み込み直後からずれている」と判定し、ステップ数の引き算がマイナス(符号なしの数で、とても大きな数)になったこと。既知の違いをそろえてから比べ、引き算の前に範囲を確かめるように直した。
- 教訓: 「違う」と出たら、まず診断の数え方・比べ方を疑う。比べる時は、既知の違いを取り除いてから比べる。長く回る診断には、時間の上限を付けて動かす。

### 6.3 見つかった以前からの問題(F2とは関係ない)
「施設 → 商業エリア」の対応表は、セーブされず、読み込みで空になり、約3秒ごとの需要の計算で作り直される。だから、ロード直後の最大約3秒は、商業エリアが無いものとして動く。
- 見つけ方: セーブ→ロードした街とそのまま進めた街を、50ステップごと → 1ステップごとに比べ、最初にずれたステップの中身を比べた。違いは、ある住民の `areasCounted`(この外出で数え済みの商業エリア)が `[1]` か `[]` か、だけだった。
- 用語: **派生データ(キャッシュ)** = 他のデータから計算し直せるので、保存しないデータ。保存しないなら、「読み込んだ直後に作り直す」か「使う前に、空なら作り直す」が必要。
- 直すのは、承認をもらってから(住民の行動の結果が変わるため)。
