# 住民シミュレーションのデバッグ基盤(段階0・1)

2026-10-29。確率で動く住民の「なぜそうなったか」を、後から読める形にした。設計と指示書との照合は [docs/design/simulation_debug_system.md](../design/simulation_debug_system.md)。ここでは、**なぜそうしたか・どう動くか・困ったこと・確かめた結果**を、自分で読み返す用にまとめる。

## 1. なぜ作ったか(困っていたこと)
外出や立ち寄りは、確率(乱数)で決まる。目で見ていると、
- 「立ち寄りが起きない」のが、**25%の抽選に外れた**のか、**体力・時刻の条件で考えなかった**のか、**候補が無かった**のかが分からない。
- 外出判定は3秒ごとに全員ぶんあるので、**不発は目に見えない**(どこにも残っていなかった)。
- 施設選びの計算(品質・値段・距離・再訪)は、結果の重みしか残らず、**どの係数が効いたか**が分からない。

→ 「結果」ではなく「**判断の過程と理由**」を残す。

## 2. 用語
| 用語 | 意味 |
|---|---|
| イベント | 意思決定・分岐・状態の変化・資源の変化・異常、のどれかが起きた記録1件(`SimEvent`)。関数を呼んだだけでは作らない |
| 判断の内訳(detail) | 施設選び1回の、候補ごとの係数・重み・確率・乱数などを丸ごと残した物(`SimDecisionDetail`) |
| 外出のまとまり(outingId) | 1回の外出の、判定から帰宅までのイベントをつなぐ番号 |
| 世界(runId) | ロード・リセットのたびに増える番号。違う世界の同じ住民id/施設idを、取り違えないために使う |
| リングバッファ | 容量の上限を決めて、いっぱいになったら古い物から捨てる記録の持ち方(`std::deque` で実装) |
| 不変条件 | 「いつでも成り立つはずの条件」(例: 体力は負にならない)。破れたら異常 |
| 立ち上がり(rising edge) | 「違反していない → している」に変わった瞬間。この時だけ記録して、続いている間は繰り返さない |
| 決定性 | 同じ入力・同じ刻みなら、同じ結果になること。**記録のON/OFFで結果が変わらない**ことを、これで確かめた |
| トレース | ルールの関数が「実際に使った値」を、呼び出し側へ書き出すこと(今回は `PurposeTrace` / `FacilityChoiceTrace` / `FacilityWeightBreakdown`) |

## 3. 仕組み(要点)
### 3.1 画面は計算し直さない(最重要)
最初に考えがちなのは、画面側で「この候補の重みは…」と式を書いて表示すること。でも、**ルールを変えた時に、画面の式だけ古いまま**になる危険がある。そこで、
```cpp
// ルールの関数が、途中の値も一緒に返す(計算は1か所)
void ComputeFacilityWeightBreakdown(..., FacilityWeightBreakdown& out);   // 係数を全部 out に書く

float ComputeFacilityWeight(...)                                          // 以前からの関数は、これを呼ぶだけ
{
    FacilityWeightBreakdown b;
    ComputeFacilityWeightBreakdown(..., b);
    return b.weight;
}
```
とした。画面は `b` の値(適性・品質係数・値段係数・距離係数…)を、文章に当てはめて出すだけ。乱数も同じで、`ChooseFacility` が引いた値を `FacilityChoiceTrace` に入れて返す(**UI側では乱数を引かない**)。

### 3.2 記録のON/OFFで、乱数の消費を変えない
トレースは「**引いた値を、変数に受けてから使う**」だけで、**引く回数・順序は同じ**にした。
```cpp
// 変更前: if (!(m_random.Next01() < chance)) continue;
const float outingRoll = m_random.Next01();      // 1回引く(以前と同じ)
const bool  outingHit  = outingRoll < chance;
if (!outingHit) { continue; }
```
食事系の連続のように、**条件によって引いたり引かなかったりする乱数**も、短絡評価(`a && !(Next01() < x)`)を、同じ条件の `if` に書き換えた(`accept < 1.0f` の時だけ引く)。

### 3.3 記録の窓口は、先頭で戻る
`DemandSystem::RecordEvent` などは、最初の行が `if (!m_debugRecorder.IsEnabled()) return 0;`。Releaseでは、記録は一度も有効にならないので、実質、何もしない。引数に重い計算が入る所(経路の長さなど)は、`IsEnabled() ? ... : 0` で守った。

### 3.4 外出判定の「不発」は、イベントにしない
全住民 × 3秒ごと。毎回イベントにすると、リングバッファが不発で埋まり、**大事な記録が押し出される**。そこで、
- 住民ごとの**集計**(判定回数・当選回数・連続の不発・直近の確率と乱数)だけ持つ。
- 「そもそも考えない時間だった」(就寝中・遅い時刻)は、**ティック全体の記録**(`SimTickGate`)として1つだけ持つ。
→ 画面の「次の外出判定」に、「確率 3.0% / 直近の判定: 乱数 0.5 → 不発 / 連続の不発 14回」が出る。

### 3.5 外れ(NotMet)と異常(Violation)を混ぜない
「25%の抽選に外れた」は**普通のこと**で、灰色。赤にすると、本物の異常が埋もれる。赤は、`CheckResidentInvariants` が**条件の破れ**を確認した時だけ。

## 4. 見つけた問題と、直し方
### 4.1 「体力が上限を超えた」は、異常ではなかった
最初は「体力が実効の上限(ペナルティで下がる)を超えたら異常」と考えた。でも `ProcessResidentWeekEnd` はペナルティの段階を上げるだけで、**今の体力は下げない**。つまり、ペナルティが付いた週に、体力が実効の上限より大きい状態は**普通に起きる**。そのまま作ると、誤検出になる。
→ 比べる相手を、**住民の基準の上限(`staminaCapBase`)**にした。単体テストに「ペナルティ3・体力95で、違反にならない」を入れた。
> 教訓: 異常検知は、「なんとなく変な値」ではなく、**コードが保証している条件**だけにする。保証していない条件は、誤検出の元。

### 4.2 帰宅中・立ち往生で、行き先が0なのは普通
`MissingTargetFacility` を「いつも行き先が必要」にすると、帰宅中で全部違反になる。**状態ごとに条件を分けた**(向かっている・利用中だけが対象)。経路が2点未満の移動も、`arrive()` が「到着」として扱う設計なので、違反にしない(添字が経路の外にある時だけ)。

### 4.3 同じセーブを読み直すと、住民の特徴が変わる(テストの罠)
決定性の確認で、最初は「同じ街を、1回の起動で、ON → OFF → ONの順に読み直して、結果を比べる」とした。結果は、**ONとONでも違った**(記録とは無関係)。
原因: 住民の特徴の種は `MakeResidentSeed(seed, house.id, index)` で、`house.id`(GameObjectのid)に依存する。**ロードのたびにidが進む**ので、生成される住民の特徴が毎回変わっていた。
→ 比べ方を変えた: **1回の起動で1回だけ**動かし、起動を4回(ON・OFF・ON・OFF)繰り返す。起動ごとのidの並びは同じなので、比べられる。
> 副産物の発見: 「ロードで必ず同じ乱数列から始まる」(種を毎回12345に戻す)だけでなく、**新しく生成される住民の特徴が、idに依存する**。再現性(段階5)で、特徴の種を何から決めるかも、見直す必要がある。

### 4.4 表が画面いっぱいに伸びた
候補の表に `ImGuiTableFlags_ScrollX`(横スクロール)を付けて、高さを指定しなかったら、**表が残りの高さいっぱいに広がり**、下に大きな空白ができた(スクリーンショットで気づいた)。
→ 高さを、`(行数 + 1) × 行の高さ + スクロールバー` で指定した。

### 4.5 ウィンドウが畳まれている間に、世界が変わる
パネルのタブが裏にある間は、`ImGui::Begin` が false を返して、描く処理を飛ばす。その間にロードされると、**古い対象のまま**になる。世界の確認は、`Begin` の前に行うようにした。

### 4.6 ツール側の注意(作業で踏んだ)
- 同じファイルへの編集を**並列**に出すと、1件だけ失敗する(OneDrive上のファイルの置き換えが競合)。同じファイルは順番に編集する。
- 編集ツールは、改行を LF で書く。さらに、改行の変換で末尾に `\r` だけが残ると、gitが**そのファイルをテキストと見なさず**、差分が全行になる(`git ls-files --eol` で `w/-text`)。末尾の `\r` を削って直した。
- スクリーンショットは、R と B が入れ替わって保存される(オレンジが青に見える)。**赤い異常表示が青に見えた**のは、これのため(実際のゲームでは赤)。

## 5. 確かめたこと(実測)
### 5.1 単体テスト(スクラッチ。リポジトリには入れていない `ut/debug1_test.cpp`)
- **重みの内訳が、以前の式と完全に同じ**: 64000通りで、新旧の `ComputeFacilityWeight` が**ビットまで一致**。内訳の積・下限も一致。
- `ChoosePurpose`(6000通り・両方不足で同じ値の場合も)・`ChooseFacility`(6000通り・除外・履歴・立ち寄りの使用済みを含む)が、**以前の実装(テストに写しを置いた)と、結果・乱数の状態まで一致**。トレースの乱数は、実際に引いた順の乱数と一致。累積の範囲は隙間なくつながり、確率の合計は1。
- 立ち寄りを考えない理由・外出を考える確率が、以前の式と一致(20000通り)。
- 記録: OFFで何も残らない、外出のまとまりの始まり・終わり、住民ごとの集計、上限での破棄と件数、判断の内訳の探索、新しい世界で消える。
- 不変条件: 正常な状態(全状態)は違反にならない、設計上ありえる状態は違反にならない、壊れた状態を種類ごとに検出、立ち上がりだけ記録。
- 既存の `sim_test`・`p1_test` も、変更後のソースで**全て合格**(回帰なし)。

### 5.2 ゲームの中(Debugビルド。12倍速。診断コードで街を読み込み。確認後に削除済み)
- **記録ON/OFFの決定性**: テスト用の街(住民6人)を、同じ入力・同じ刻み(0.1秒×12000回 = 111週)で動かした。

| 記録 | 状態のハッシュ | 乱数の内部状態 | 利用回数 | イベント |
|---|---|---|---|---|
| ON | `9236011079f121f5` | `450ea1ba` | 1777 | 15056件 |
| OFF | `9236011079f121f5` | `450ea1ba` | 1777 | 0件 |
| ON(2回目) | 同じ | 同じ | 同じ | 同じ |
| OFF(2回目) | 同じ | 同じ | 同じ | 0件 |

(ハッシュは、全住民の状態・位置・体力・需要・履歴数・来客と売上・乱数の状態・時計。)
- **誤検出なし**: 111週で、異常は0件(状態が壊れていないので正しい)。施設を解体(歩いている途中)→ 3000ステップ、住宅を解体 → 3000ステップでも、異常は0件。
- **解体時のイベント**: 行き先の施設を解体すると、`OutingAborted`(注意・黄)が、解体前の状態の写し(移動中)で記録された。
- **異常の検出**: 体力を `-5` に壊すと、次のティックで `Anomaly`(違反・赤)が1件。パネルの「異常」タブと、上の赤い帯に出た。直るまで、繰り返し記録されない。
- **選択との連動**: 住民を選ぶ → パネルの対象がその住民。住宅を選ぶ(追従なし)→ その住宅の住民(#14 → 住民 #24)。街を読み込み直すと、記録の世界番号が変わり、住民も入れ替わった(診断では、パネルの対象が古いままになる不具合を見つけ、世界の確認を `Begin` の前へ移して直した。**直した後の実機での再確認は、していない**)。
- **初期配置**: 「レイアウトを初期化」で、「住民デバッグ」は下のタブ(City Stats の隣)に入る。
- **ビルド**: Debug・Release とも、リビルドで警告・エラーなし。Releaseは起動して8秒動いた(落ちない)。
- **メモリ**: イベント15056件+判断の内訳1793件で約2.9MB。構造体の大きさ: イベント104バイト、判断の内訳376バイト+候補120バイトずつ。

### 5.3 まだ確かめていないこと(正直に)
- **実際のマウスクリック**での選択→パネルの切り替え(クリックの処理は変えていない。診断では、クリックが書き込む変数 `m_followAgentId` / `m_selectedBuildingId` を直接設定して確かめた)。実機で、1回クリック・2回クリック(情報パネルが開く)を、手で確かめてほしい。
- 住民が多い街(数十〜数百人)での、記録の負荷と、イベント上限での見え方。`CheckAllInvariants` は、ティックごとに全住民を1回なぞる(物の表は1回だけ作る)。
- 道路を切り取った時(`OnRoadsChanged`)の、迂回・立ち往生のイベントを、ゲーム内では確かめていない(コードは入れてある。以前の手動確認の経路と同じ関数)。
- 長時間・大量のイベントでの、パネルの描画の重さ(処理履歴は、直近500件までを読む)。

## 6. 今後の課題(段階2以降の準備)
- 履歴の閲覧(シークバー)は、**イベントに写しを持たせた**ので、「その時の値」を出せる土台はある。
- 既存の City Stats > Decisions(40件)と、新しい判断の内訳が重複している。段階2以降で、どちらかに寄せる。
- 乱数の保存・復元(段階5)には、`SimRandom::GetState()`(今回、読み取りだけ足した)の、書き込み側が要る。ロードで毎回同じ種(12345)から始まる点と、住民の特徴の種が id に依存する点も、一緒に見直す。
