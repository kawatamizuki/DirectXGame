# 住民シミュレーションのデバッグ基盤(段階0・1)

2026-10-29。確率で動く住民の「なぜそうなったか」を、後から読める形にした。設計と指示書との照合は [docs/design/simulation_debug_system.md](../design/simulation_debug_system.md)。ここでは、**なぜそうしたか・どう動くか・困ったこと・確かめた結果**を、自分で読み返す用にまとめる。

## 1. なぜ作ったか(困っていたこと)
外出や立ち寄りは、確率(乱数)で決まる。目で見ていると、
- 「立ち寄りが起きない」のが、**25%の抽選に外れた**のか、**体力・時刻の条件で考えなかった**のか、**候補が無かった**のかが分からない。
- 外出判定は3秒ごとに全員ぶんあるので、**不発は目に見えない**(どこにも残っていなかった)。
- 施設選びの計算(品質・値段・距離・再訪)は、結果の重みしか残らず、**どの係数が効いたか**が分からない。

→ 「結果」ではなく「**判断の過程と理由**」を残す。

## 2. 用語
| 用語 | 意味 |
|---|---|
| イベント | 意思決定・分岐・状態の変化・資源の変化・異常、のどれかが起きた記録1件(`SimEvent`)。関数を呼んだだけでは作らない |
| 判断の内訳(detail) | 施設選び1回の、候補ごとの係数・重み・確率・乱数などを丸ごと残した物(`SimDecisionDetail`) |
| 外出のまとまり(outingId) | 1回の外出の、判定から帰宅までのイベントをつなぐ番号 |
| 世界(runId) | ロード・リセットのたびに増える番号。違う世界の同じ住民id/施設idを、取り違えないために使う |
| リングバッファ | 容量の上限を決めて、いっぱいになったら古い物から捨てる記録の持ち方(`std::deque` で実装) |
| 不変条件 | 「いつでも成り立つはずの条件」(例: 体力は負にならない)。破れたら異常 |
| 立ち上がり(rising edge) | 「違反していない → している」に変わった瞬間。この時だけ記録して、続いている間は繰り返さない |
| 決定性 | 同じ入力・同じ刻みなら、同じ結果になること。**記録のON/OFFで結果が変わらない**ことを、これで確かめた |
| トレース | ルールの関数が「実際に使った値」を、呼び出し側へ書き出すこと(今回は `PurposeTrace` / `FacilityChoiceTrace` / `FacilityWeightBreakdown`) |

## 3. 仕組み(要点)
### 3.1 画面は計算し直さない(最重要)
最初に考えがちなのは、画面側で「この候補の重みは…」と式を書いて表示すること。でも、**ルールを変えた時に、画面の式だけ古いまま**になる危険がある。そこで、
```cpp
// ルールの関数が、途中の値も一緒に返す(計算は1か所)
void ComputeFacilityWeightBreakdown(..., FacilityWeightBreakdown& out);   // 係数を全部 out に書く

float ComputeFacilityWeight(...)                                          // 以前からの関数は、これを呼ぶだけ
{
    FacilityWeightBreakdown b;
    ComputeFacilityWeightBreakdown(..., b);
    return b.weight;
}
```
とした。画面は `b` の値(適性・品質係数・値段係数・距離係数…)を、文章に当てはめて出すだけ。乱数も同じで、`ChooseFacility` が引いた値を `FacilityChoiceTrace` に入れて返す(**UI側では乱数を引かない**)。

### 3.2 記録のON/OFFで、乱数の消費を変えない
トレースは「**引いた値を、変数に受けてから使う**」だけで、**引く回数・順序は同じ**にした。
```cpp
// 変更前: if (!(m_random.Next01() < chance)) continue;
const float outingRoll = m_random.Next01();      // 1回引く(以前と同じ)
const bool  outingHit  = outingRoll < chance;
if (!outingHit) { continue; }
```
食事系の連続のように、**条件によって引いたり引かなかったりする乱数**も、短絡評価(`a && !(Next01() < x)`)を、同じ条件の `if` に書き換えた(`accept < 1.0f` の時だけ引く)。

### 3.3 記録の窓口は、先頭で戻る
`DemandSystem::RecordEvent` などは、最初の行が `if (!m_debugRecorder.IsEnabled()) return 0;`。Releaseでは、記録は一度も有効にならないので、実質、何もしない。引数に重い計算が入る所(経路の長さなど)は、`IsEnabled() ? ... : 0` で守った。

### 3.4 外出判定の「不発」は、イベントにしない
全住民 × 3秒ごと。毎回イベントにすると、リングバッファが不発で埋まり、**大事な記録が押し出される**。そこで、
- 住民ごとの**集計**(判定回数・当選回数・連続の不発・直近の確率と乱数)だけ持つ。
- 「そもそも考えない時間だった」(就寝中・遅い時刻)は、**ティック全体の記録**(`SimTickGate`)として1つだけ持つ。
→ 画面の「次の外出判定」に、「確率 3.0% / 直近の判定: 乱数 0.5 → 不発 / 連続の不発 14回」が出る。

### 3.5 外れ(NotMet)と異常(Violation)を混ぜない
「25%の抽選に外れた」は**普通のこと**で、灰色。赤にすると、本物の異常が埋もれる。赤は、`CheckResidentInvariants` が**条件の破れ**を確認した時だけ。

## 4. 見つけた問題と、直し方
### 4.1 「体力が上限を超えた」は、異常ではなかった
最初は「体力が実効の上限(ペナルティで下がる)を超えたら異常」と考えた。でも `ProcessResidentWeekEnd` はペナルティの段階を上げるだけで、**今の体力は下げない**。つまり、ペナルティが付いた週に、体力が実効の上限より大きい状態は**普通に起きる**。そのまま作ると、誤検出になる。
→ 比べる相手を、**住民の基準の上限(`staminaCapBase`)**にした。単体テストに「ペナルティ3・体力95で、違反にならない」を入れた。
> 教訓: 異常検知は、「なんとなく変な値」ではなく、**コードが保証している条件**だけにする。保証していない条件は、誤検出の元。

### 4.2 帰宅中・立ち往生で、行き先が0なのは普通
`MissingTargetFacility` を「いつも行き先が必要」にすると、帰宅中で全部違反になる。**状態ごとに条件を分けた**(向かっている・利用中だけが対象)。経路が2点未満の移動も、`arrive()` が「到着」として扱う設計なので、違反にしない(添字が経路の外にある時だけ)。

### 4.3 同じセーブを読み直すと、住民の特徴が変わる(テストの罠)
決定性の確認で、最初は「同じ街を、1回の起動で、ON → OFF → ONの順に読み直して、結果を比べる」とした。結果は、**ONとONでも違った**(記録とは無関係)。
原因: 住民の特徴の種は `MakeResidentSeed(seed, house.id, index)` で、`house.id`(GameObjectのid)に依存する。**ロードのたびにidが進む**ので、生成される住民の特徴が毎回変わっていた。
→ 比べ方を変えた: **1回の起動で1回だけ**動かし、起動を4回(ON・OFF・ON・OFF)繰り返す。起動ごとのidの並びは同じなので、比べられる。
> 副産物の発見: 「ロードで必ず同じ乱数列から始まる」(種を毎回12345に戻す)だけでなく、**新しく生成される住民の特徴が、idに依存する**。再現性(段階5)で、特徴の種を何から決めるかも、見直す必要がある。

### 4.4 表が画面いっぱいに伸びた
候補の表に `ImGuiTableFlags_ScrollX`(横スクロール)を付けて、高さを指定しなかったら、**表が残りの高さいっぱいに広がり**、下に大きな空白ができた(スクリーンショットで気づいた)。
→ 高さを、`(行数 + 1) × 行の高さ + スクロールバー` で指定した。

### 4.5 ウィンドウが畳まれている間に、世界が変わる
パネルのタブが裏にある間は、`ImGui::Begin` が false を返して、描く処理を飛ばす。その間にロードされると、**古い対象のまま**になる。世界の確認は、`Begin` の前に行うようにした。

### 4.6 ツール側の注意(作業で踏んだ)
- 同じファイルへの編集を**並列**に出すと、1件だけ失敗する(OneDrive上のファイルの置き換えが競合)。同じファイルは順番に編集する。
- 編集ツールは、改行を LF で書く。さらに、改行の変換で末尾に `\r` だけが残ると、gitが**そのファイルをテキストと見なさず**、差分が全行になる(`git ls-files --eol` で `w/-text`)。末尾の `\r` を削って直した。
- スクリーンショットは、R と B が入れ替わって保存される(オレンジが青に見える)。**赤い異常表示が青に見えた**のは、これのため(実際のゲームでは赤)。

## 5. 確かめたこと(実測)
### 5.1 単体テスト(スクラッチ。リポジトリには入れていない `ut/debug1_test.cpp`)
- **重みの内訳が、以前の式と完全に同じ**: 64000通りで、新旧の `ComputeFacilityWeight` が**ビットまで一致**。内訳の積・下限も一致。
- `ChoosePurpose`(6000通り・両方不足で同じ値の場合も)・`ChooseFacility`(6000通り・除外・履歴・立ち寄りの使用済みを含む)が、**以前の実装(テストに写しを置いた)と、結果・乱数の状態まで一致**。トレースの乱数は、実際に引いた順の乱数と一致。累積の範囲は隙間なくつながり、確率の合計は1。
- 立ち寄りを考えない理由・外出を考える確率が、以前の式と一致(20000通り)。
- 記録: OFFで何も残らない、外出のまとまりの始まり・終わり、住民ごとの集計、上限での破棄と件数、判断の内訳の探索、新しい世界で消える。
- 不変条件: 正常な状態(全状態)は違反にならない、設計上ありえる状態は違反にならない、壊れた状態を種類ごとに検出、立ち上がりだけ記録。
- 既存の `sim_test`・`p1_test` も、変更後のソースで**全て合格**(回帰なし)。

### 5.2 ゲームの中(Debugビルド。12倍速。診断コードで街を読み込み。確認後に削除済み)
- **記録ON/OFFの決定性**: テスト用の街(住民6人)を、同じ入力・同じ刻み(0.1秒×12000回 = 111週)で動かした。

| 記録 | 状態のハッシュ | 乱数の内部状態 | 利用回数 | イベント |
|---|---|---|---|---|
| ON | `9236011079f121f5` | `450ea1ba` | 1777 | 15056件 |
| OFF | `9236011079f121f5` | `450ea1ba` | 1777 | 0件 |
| ON(2回目) | 同じ | 同じ | 同じ | 同じ |
| OFF(2回目) | 同じ | 同じ | 同じ | 0件 |

(ハッシュは、全住民の状態・位置・体力・需要・履歴数・来客と売上・乱数の状態・時計。)
- **誤検出なし**: 111週で、異常は0件(状態が壊れていないので正しい)。施設を解体(歩いている途中)→ 3000ステップ、住宅を解体 → 3000ステップでも、異常は0件。
- **解体時のイベント**: 行き先の施設を解体すると、`OutingAborted`(注意・黄)が、解体前の状態の写し(移動中)で記録された。
- **異常の検出**: 体力を `-5` に壊すと、次のティックで `Anomaly`(違反・赤)が1件。パネルの「異常」タブと、上の赤い帯に出た。直るまで、繰り返し記録されない。
- **選択との連動**: 住民を選ぶ → パネルの対象がその住民。住宅を選ぶ(追従なし)→ その住宅の住民(#14 → 住民 #24)。街を読み込み直すと、記録の世界番号が変わり、住民も入れ替わった(診断では、パネルの対象が古いままになる不具合を見つけ、世界の確認を `Begin` の前へ移して直した。**直した後の実機での再確認は、していない**)。
- **初期配置**: 「レイアウトを初期化」で、「住民デバッグ」は下のタブ(City Stats の隣)に入る。
- **ビルド**: Debug・Release とも、リビルドで警告・エラーなし。Releaseは起動して8秒動いた(落ちない)。
- **メモリ**: イベント15056件+判断の内訳1793件で約2.9MB。構造体の大きさ: イベント104バイト、判断の内訳376バイト+候補120バイトずつ。

### 5.3 まだ確かめていないこと(正直に)
- **実際のマウスクリック**での選択→パネルの切り替え(クリックの処理は変えていない。診断では、クリックが書き込む変数 `m_followAgentId` / `m_selectedBuildingId` を直接設定して確かめた)。実機で、1回クリック・2回クリック(情報パネルが開く)を、手で確かめてほしい。
- 住民が多い街(数十〜数百人)での、記録の負荷と、イベント上限での見え方。`CheckAllInvariants` は、ティックごとに全住民を1回なぞる(物の表は1回だけ作る)。
- 道路を切り取った時(`OnRoadsChanged`)の、迂回・立ち往生のイベントを、ゲーム内では確かめていない(コードは入れてある。以前の手動確認の経路と同じ関数)。
- 長時間・大量のイベントでの、パネルの描画の重さ(処理履歴は、直近500件までを読む)。

## 7. 段階2: 履歴の見返しと、一時停止
設計は [docs/design/simulation_debug_system.md](../design/simulation_debug_system.md) の §8。

### 7.1 用語
| 用語 | 意味 |
|---|---|
| シークバー | 動画の再生バーのような、ドラッグで位置を選ぶ部品の名前。ここでは、**記録されたイベントの並び**の、どれを見るかを選ぶ。街の時刻や状態は、動かさない |
| カーソル | 履歴で「今見ているイベント」(`m_cursorEventId`)。ライブでは、いつも最新のイベント |
| ライブ / 履歴 | 最新を追う / 過去を固定して読む。履歴を見ている間に、新しいイベントが来ても、表示は動かない |
| ブックマーク | 後で戻りたいイベントの目印(番号を覚える) |
| ブレークポイント | 「この条件のイベントが起きたら、止める」という指定。デバッガーのブレークポイントと同じ考え方(`SimBreakpoints`) |
| 安全な境界 | 処理の途中ではなく、1回分の更新が済んだ所。ここなら、状態が中途半端でない |

### 7.2 なぜ「巻き戻し」ではなく「閲覧」か
街を過去の状態へ戻すには、全住民・施設・道路・乱数の状態を、毎回保存して、復元する必要がある(大きな仕事で、ずれると、本物のバグの元になる)。一方、知りたいのは「**その時、なぜそう判断したか**」で、これは、イベントとその時の写し(スナップショット)を残してあれば、読める。そこで、**記録を読む道具**に絞った。
- 「現在」タブの履歴モードでは、**写しにある値だけ**を出し、無い値(位置・経路など)は「出せません」と書く。補間して、あたかも正確に分かっていたように見せない。

### 7.3 一時停止の作り
```
DemandSystem::Update ─ イベントを記録(AddEvent) ─ 条件に合えば「止める印」を立てる(記録部)
        ↓ 更新が済んだ後(安全な境界)
Game::Update: 印があれば、SyncMenuTimeScale() で、時間を止める
```
- **記録部は、止めない**。印を立てるだけにして、シミュレーションの結果・乱数に、一切触れない(記録のON/OFFで結果が変わらない約束を、守る)。
- **止める処理は、既存のものに相乗り**した。メニュー・パネル・配置ツールの停止は、「止める前の倍率を1回覚えて、止める物が全部無くなったら戻す」仕組み(`SyncMenuTimeScale`)。ここに「デバッグの停止」を1項目足しただけなので、**メニューを開閉しても、倍率が壊れない**(実機で確認)。別の方法(専用の変数で倍率を保存する)にすると、2つの仕組みが倍率を取り合って、0のまま戻らなくなる危険がある。
- **更新の直後に、すぐ止める**。次のフレームの `UpdateGameUI` を待つと、12倍速では、1フレームで、ゲーム内の時間が大きく進む。

### 7.4 見つけた問題と、直し方
- **「判断の詳細」が、最初の判断に固定されていた**(段階1の不具合): 選択中の判断を、毎フレーム「今の選択」に上書きしていたので、新しい判断が来ても、最新に追従しなかった。→ 「自分で選んだか」(`m_decisionManual`)を持ち、ライブで、自分で選んでいない間は、いつも最新にした。履歴のカーソルを動かすと、その時点の判断に合わせる。
- **処理履歴が、新しい順だと、読んでいる最中に、行がずれる**: 新しいイベントが上に積まれるので、履歴を見ている間に、勝手に動く(指示書の「勝手に最新へスクロールしない」に反する)。→ **古い順**に並べ、ライブで一番下まで読んでいる時だけ、下へ追いかける(普通のログビューアーと同じ)。履歴では、カーソルの行へ1回だけスクロールする。
- **カーソルの古い判断が、コンボの一覧(最新の40件)に無い**: 一覧から探すと、見つからず、最新に戻ってしまう。→ 一覧に無い判断は、記録全体から探す。
- **フォントに無い記号**: ★ ☆ ▲ は、日本語の文字範囲に入っているか不確かなので、文字化け(四角)を避けて、使わなかった(「ブックマークする」と文字で書き、バーの三角は、図形で描いた)。
- **カーソルのイベントが、絞り込みで外れる**: 時間軸に無いので、位置が決まらない。→ それより前の一番近いイベントに寄せる。先頭より古い(捨てられた)時は、先頭に寄せて、その旨を出す。

### 7.5 確かめたこと
- **単体テスト**(スクラッチ `debug2_test`): 全て合格。
  - 止める条件: 異常のみ/注意以上/種類+結果(立ち寄りの当選だけ)/住民の絞り込みが全ての条件に掛かる/条件が無ければ止めない。
  - 記録部の印: 最初の1件だけ立つ/解除で外れる/OFF・新しい世界で外れる(条件は残る)/捨てられたイベントは探しても無い。
  - 時間軸: 住民ごと・古い順・絞り込み/外出のまとまりの前後(外出に属さない記録を含む)/カーソルの位置(絞り込みで外れた時・先頭より古い時・空)/前後の一致(注意・ブックマーク)。
- 段階1のテスト(`debug1_test`)も、変更後に全て合格(回帰なし)。
- **ゲーム内**(Debugビルド・12倍速。診断コードで、条件=「立ち寄り判定 + 成功」、立ち寄りの確率を100%にして実行。確認後に削除済み):
  - 条件に当てはまったフレームで、**その場で倍率が0になった**(`PAUSED at frame 78: ... timeScale=0.0`)。止めた住民と、パネルの対象が一致した。
  - 止まっている間に、**メニューを開いて閉じても、止まったまま**。「再開」で、**元の倍率(12)に戻った**。これを、約17回繰り返して、毎回同じ。
  - 止まった瞬間に、パネルは、そのイベントを履歴として開いた(シークバー・「ライブに戻る」・「現在の街は巻き戻っていません」の表示。画面で確認)。
- Debug・Releaseとも、リビルドで警告・エラーなし。Releaseは起動して8秒動いた。

## 8. 段階3: 行動テスト
設計は [docs/design/simulation_debug_system.md](../design/simulation_debug_system.md) の §9。

### 8.1 用語
| 用語 | 意味 |
|---|---|
| コマンド(指示) | 画面が作る「何を・誰に・どう実行するか」のまとまり(`SimTestCommand`)。画面は、これを渡すだけ |
| 計画(プラン) | 指示を、住民1人ぶんに分けた物(`SimTestPlan`)。待機中のまま、次の安全なタイミングを待つ |
| キュー(待ち行列) | 計画を、いったん溜めておく入れ物。画面から直接、住民の内部を触らず、**シミュレーションの更新の中の決まった所**で1回だけ消化する |
| 強制 | 確率の抽選・候補の選択など、**1つの判定だけ**を、指定どおりの結果にすること。他の条件(時刻・体力・到達)は、通常どおり調べる |
| 拒否 | 通常ルールに合わなくて、実行しなかったこと。バグではない。理由を、結果に残す |
| テスト番号(`testId`) | 計画に付く通し番号。計画の間に記録するイベントに付けて、後で、テスト由来と見分ける |
| 置き換え(Superseded) | 実行中の計画を、新しい指示で取り消すこと |

### 8.2 なぜ「キュー」にしたか
画面のコード(ImGui)が、住民の状態を直接書き換えると、①シミュレーションの更新の途中で状態が変わって、中途半端になる ②どの時点で変わったか、記録できない ③乱数の消費の順番が、画面を描く順番に依存する、という問題が起きる。そこで、**画面は指示を出すだけ**にして、`DemandSystem` が、外出判定・立ち寄り判定・更新の最初という**決まった所**で、計画を1回だけ消化する形にした(段階2の「止める印」と同じ考え方)。

### 8.3 乱数を乱さない工夫
強制する時も、**抽選の乱数は、必ず1つ引く**(`const float roll = m_random.Next01(); const bool natural = roll < chance;` を先に計算し、`hit = natural || テストの強制`)。強制の有無で乱数の消費の数が変わると、**テストしていない他の住民の動きまで、変わってしまう**。外出の判定も、立ち寄りの判定も、同じ作りにした。

### 8.4 見つけた問題と、直し方
- **外出させた後に、続けて指示が出せなかった**: 「外出させる」(立ち寄り0回)の計画は、外出が終わるまで「実行中」なので、その間は「別のテストが実行中」で拒否されていた(ゲーム内の診断で発覚)。→ **実行中の計画は、新しい指示で置き換える**(取消。理由は「置き換え」)ようにした。待機中の計画は、置き換えない。
- **長い説明が、右で切れた**: 薄い色の説明文を `TextDisabled` で出すと、折り返さない。→ 色を替えた `TextWrapped` の小さな関数にした。
- **取消の理由が、表に出なかった**: 取消でも、理由(置き換え)があるのに、「-」と出していた。→ 取消で理由がある時は、理由を出す。
- **ヘッダーの include 漏れ**: `ResidentDebugPanel.h` が、`SimTestSubmitResult` を持つのに、`SimTest.h` を include していなかった(ビルドで発覚)。

### 8.5 確かめたこと
- **単体テスト**(スクラッチ `debug3_test`): 全て合格。対象の選び方(今の住民=一覧に居る時だけ/範囲=辺を含む・min/maxが逆でも同じ/全住民/人数の上限=1〜500に丸める・切り捨てを知らせる)、状態の判定、記録部のテスト番号(付く・外れる・別の住民には付かない・OFFでは付かない・新しい世界で消える・外す時に記録を新しく作らない)。段階1・2のテストも、回帰なし。
- **ゲーム内**(Debugビルド・20倍速。診断コードで確認。確認後に削除済み):
  - 外出させる(通常ルール・立ち寄り2回): 外出の判定→目的選択→施設選択→移動の一連のイベントに、`[テスト#1]` が付いた。立ち寄りは、時刻などの条件で拒否された時に、**拒否の理由**(立ち寄りを考えない条件・食事系の連続)が出た。
  - 施設を指定して外出: 全施設で成功(判断の内訳に、強制の印)。体力を2にしてから、遠い施設を指定すると、**「指定した施設は除外された」で拒否**(理由の番号つき)。
  - 全住民(6人)に外出: 6人とも成功。出した直後に取消: 6件が取消になり、待機中が0になった。
  - 家にいる住民に「帰宅させる」→ 拒否(外出中でない)。外出中に「外出させる」→ 拒否(家にいない・今の状態つき)。外出中に「帰宅させる」→ 成功(帰宅した)。外出中に「行き先を変える」→ 成功。外出中に「立ち寄りを当選させる」→ 成功(1/1)。体力を5にする → 成功(6.8になっていた=少し回復した後の値)。
  - 範囲が空(誰もいない): 対象0人、実行しない。
  - 実行中の計画を、新しい指示で置き換えられることを確認。
  - **画面**(診断で、バックバッファを保存): 行動テストのタブ(5つの見出し・説明の折り返し・結果の表の色・[履歴]ボタン)を確認。
- Debug・Releaseとも、リビルドで警告・エラーなし(Renderer.cpp の既存の警告のみ)。

### 8.6 まだ確かめていないこと
- 実際のマウスでの操作(範囲の入力・確認の画面・取消ボタン)。ロジックは、診断・単体テストで確認した。

## 9. 段階4: 行動統計
設計は [docs/design/simulation_debug_system.md](../design/simulation_debug_system.md) の §10。

### 9.1 用語
| 用語 | 意味 |
|---|---|
| カウンター | 件数を1つ足すだけの変数。イベントを全部溜めて後で数えるのではなく、起きた時に足していく(軽い。古いイベントを捨てても減らない) |
| 観察者(オブザーバー) | 「何かが起きた」という知らせを受け取る側。記録部が、統計に「イベントが追加された」と知らせる。記録部は、統計の中身を知らない(`ISimRecordObserver`) |
| 分母 | 率(割合)の「全体」の数。「立ち寄りの当選率」なら、「抽選した回数」。分母が違うと、同じ件数でも率が変わるので、必ず並べて出す |
| 排他(的) | 重ならないこと。1回の判定を、ちょうど1つの結果にだけ数える(合計が、判定の回数になる) |
| 期待値 | 確率どおりなら、平均で何回当選するか。各判定の確率を足し合わせた値 |
| 標準偏差(σ) | 当選数のばらつきの目安。期待値から±2σの範囲に、約95%の確率で収まる。ここを外れたら、確率が違う(または、強制・設定変更が入っている)可能性がある |
| 95%の範囲(Wilsonの信頼区間) | 「実際の率が、この範囲のどこかにある」と、約95%言える範囲。件数が少ないと広い |

### 9.2 なぜ「イベントを後で数える」のではなく、「カウンターを足す」か
記録(住民デバッグ)は、上限(イベント20000件)で古いものを捨てる。後でイベントを数える方式だと、長く動かすほど、統計が捨てられた分だけ、減って(ずれて)しまう。そこで、**イベントが記録される瞬間に、カウンターを足す**。捨てられても、統計は減らない。
- 記録部は `ISimRecordObserver` という窓口(インターフェース)を持ち、統計がそれを実装する。記録部が統計を直接持つと、ヘッダーが循環する(統計が `SimEvent` を使い、記録部が統計を持つ)ので、窓口を挟んで、依存を一方向にした。将来、別の集計を足したい時も、観察者を増やすだけでよい。

### 9.3 「最初の不成立の理由」で数える(二重計上を防ぐ)
立ち寄りの判定は、1回で、複数の理由に当てはまり得る(時刻が遅い、かつ、体力が足りない、など)。コードは、**最初に当てはまった1つ**で止まる。統計も、この「最初の理由」だけを数える(合計が判定の回数と一致する)。
- 単体テストと、ゲーム内の診断で、**「どの結果の合計」も「立ち寄りを考えた回数」と一致する**ことを確認した。
- 「当選」は、通過点(この後、候補が無い・全て除外・食事系で取りやめ、のどれかで落ちることもある)なので、最終結果の一覧には入れず、「抽選の表」(期待値と並べる)にだけ出した。

### 9.4 通常とテストを分ける
行動テストで強制した流れのイベントには、`testId` が付いている(段階3)。統計は、`testId != 0` のイベント・判断の内訳を、**「テスト」の範囲**に数える。外出判定の抽選は、強制の有無に関わらず「本当の抽選の結果」だけを、「通常」に数える(強制した当選を数えると、確率より当選が多く見えるため)。テストの範囲の立ち寄りの抽選は、強制を含むので、期待値と比べない(画面に、そう書く)。
- 注意: 強制した外出が、同じタイミングの自然な当選と重なった時は、その外出は「テスト」に数えられる(その時の抽選の当選は、「通常」に数えるので、「通常」で、当選数が、外出を考え始めた数より少し多いことがありえる)。

### 9.5 見つけた問題と、直し方
- **名前の衝突**: 既に `DemandSystem::GetStats()`(City Stats の需要の集計)が有った。→ 新しい方を `GetBehaviorStats()` にした。
- **ヘッダーの循環**: 記録部が統計を持つと、`SimStats.h` ↔ `SimDebugRecorder.h` が互いに include する。→ 観察者の窓口にした(§9.2)。
- **ファイルの改行・BOM**: 新しいファイルは、既存のファイルに合わせて、UTF-8(BOMつき)・CRLFにした(日本語のコメントの文字化けと、差分が全行に出るのを防ぐ)。
