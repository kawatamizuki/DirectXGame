# 商業エリアの区画(P2-A)

2026-11-09。商業エリアの計画区画と周知(P2-A)を実装した。設計の表は [docs/design/commercial_area.md](../design/commercial_area.md)。

## 1. 用語
| 用語 | 意味 |
|---|---|
| 区画 | プレイヤーが地面に置く、軸に沿った正方形の枠。仮置き(非公開)と周知済みがある |
| 周知 | 区画の計画を、住民に知らせること。周知した週から猶予を数え、計画規模を固定する |
| 所属 | ある商業施設が、ある区画の店舗として数えられること。1軒は、1つの区画にだけ |
| 計画達成率 | 店舗数 ÷ 計画規模。店の数だけで、集客力とは別 |
| 達成状態 | 周知後に、一度でも届いた、一番高い進捗の段階。店が減っても、下がらない |
| 撤回 | 周知済みの区画を削除すること。記録が残る |
| 敷地(footprintRect) | 建物が占める向き付きの矩形。区画との重なり面積の計算に使う |
| Sutherland–Hodgman法 | 多角形を、直線(半平面)で切り取って、残りの多角形を求める方法。矩形4辺で切る |

## 2. 設計で悩んだ点
- **所属を、保存するか・求めるか**: 保存すると、建物の解体・建築・区画の移動のたびに、IDの付け替え・古い所属の掃除が要り、セーブの建物のuidとも結び付く。→ **保存せず、毎フレーム、位置から求める**(区画・施設は数が少なく、安い)。建築・解体・移動に、自動で追従する。
- **二重所属の防ぎ方**: 区画どうしが重ならなければ、割合の合計は1以下。2つの区画が、どちらも50%以上になるのは、ちょうど50%ずつの時だけ。→ その時は、IDが小さい区画に決める(同じ結果になる、決定的な規則)。さらに、重なる区画を、そもそも置けない・読み込まない、ようにして、二重に守る。
- **面積での判定**: 制作者の指定で、中心の位置ではなく、敷地面積の50%以上。軸に沿った矩形(区画)と、回転した矩形(敷地)の重なり面積は、敷地の4隅を、区画の4辺で、順に切り取って、残った多角形の面積(靴ひも公式)を求める。丸め誤差は、`double` で計算し、50%ちょうどは、許容(1e-6)で、所属にする。
- **進捗と魅力の分離**: 仕様書の「計画達成率と実際の商業的魅力は別物」。画面に、「店の数だけを数えます。集客力・売上とは別です」と書き、魅力の値は、P2-A では、持たない。
- **周知後の履歴**: 周知後の移動・撤回を、罰則逃れにしないため、履歴と撤回の記録を、保存する(減点は、P2-D)。進捗・猶予は、移動でリセットしない。
- **パネルを、画面全体を覆わない形に**: 既存のパネル(住民の情報・入居者)は、画面全体を覆う(モーダル)。区画は、地面を見ながら動かすので、画面の右の小さなパネルにし、カーソルがパネルの上にある時だけ、ゲームへの入力を止めた。確認の手順(はい/やめる)は、パネルの中で、2段階にした。

## 3. 使った技術
- 純粋な規則(`CommercialArea.h/.cpp`)と、状態・保存(`CommercialAreaManager`)と、入力・描画(`AreaToolController`)と、UI(`AreaPanel`)を、分けた。規則と状態は、画面に依存せず、単体テストできる(`tests/sim_area_test.cpp`)。
- 画面の表示は、モデル(`AreaPanelModel`)を作って渡し、パネルは、配置と入力だけを持つ(既存のUIと同じ作法)。見た目はスキン(`IUISkin`)経由で、アイコンも、スキンに足した。
- 枠の描画は、既存の `DebugRenderer`(線)を使う。

## 4. 見つけた問題と、直し方
- **プロジェクトファイルを、スクリプトで書き換えて、全行が変わった**: 改行コードの違いで、全行の差分になった。バックアップから戻し、編集ツールで、8項目だけ足した。
- **実機で、「区画あり・なし」の指紋が、一致しなかった**: 原因は、区画ではなく、(1)ロードごとに、乱数を引き直す設定、(2)1回目の試験の後、ゲームの時間が少し進んでから、2回目の基点を取っていた、の2つ。→ 乱数を「保存した状態から復元」にし、ゲーム内の時間を止め、2回とも同じ手順(保存→読み込み)を通して比べたら、一致した(1684イベント・異常0)。**比べ方の条件を揃える大切さ**。
- **パネルの注記が、枠からはみ出した**: 実機の画面で見つけた。文を短くした。
- **画面の確認が、できなかった**: スクリーンショットの仕組みが無かったので、診断用に、一時的な画面保存(BMP)を、レンダラーに足して確認し、確認後に削除した。

## 5. 確かめたこと
- 単体テスト(`sim_area_test`): 重なり面積(軸に沿う・45度の回転・辺が接する・角・区画より大きい敷地)、所属のしきい値(ちょうど50%・49.9%・しきい値の変更)、中心が区画の中でも50%未満は所属しない、住宅・オフィスは対象外、隣接する区画での二重所属なし(ちょうど50%/50%はID小さい方)、順序に依らない、点検、進捗の段階、仮置き・移動・削除・周知(未周知は履歴なし・周知後の移動は履歴・撤回の記録・IDの再利用なし)、建物の増減・区画の移動への追従、達成状態が下がらない、保存・読み込み(往復・長さの基準・古いセーブ・壊れた項目)。
- 実機(Debug、保存した街): 古いセーブ(区画なし)の読み込み → 区画0。区画の仮置き(2つ・隣接)・重なる場所には置けない・周知・所属3軒・点検0件・保存→読み込みで一致・12週の耐久試験で、区画あり・なしの指紋が一致(異常0)。画面で、区画の枠(水色=非公開・金色=周知済み・選んだ区画は二重の枠・所属する施設の白い枠)と、「エリア」パネルが、期待どおり出る。
- Debug・Release とも、新しい警告なしでビルド。

## 6. まだ確かめていないこと・限界
- **実際のマウス操作**(クリックで置く・ドラッグで動かす・パネルのボタンを押す・周知の確認の2段階)は、操作を送らず、状態を直接つくって確かめた。入力の処理そのものは、手で触って見ていない。
- 周知の確認の画面(「周知しますか?」)の見た目は、画面で確認していない(配置の計算は、他のパネルと同じ)。
- 区画の大きさ・形は、固定の正方形だけ。道路の向きに沿った斜めの区画は、将来。
- 区画が、実際の建物の多い大きな街で、どう見えるか・操作しやすいか、は未確認(住民6人・建物10棟の街だけ)。
- 数値は全て仮(計画規模 8・段階 4/6/8・猶予 8週・50%)。

## 7. P2-B: 施設構成の評価(2026-11-09)
### 7.1 用語
| 用語 | 意味 |
|---|---|
| 供給量 | 用途ごとの、所属施設の適性(元の値)の合計。店が増えれば増える「量」 |
| 割合 | 供給量を合計で割った分布(合計1)。店の数に依らない「構成」 |
| 専門性 / 汎用性 | 1つの用途への偏り(一番大きい割合と、均等の差)。汎用性は 1 − 専門性。どちらが有利、は無い |
| 用途の充実度 | 強い店がある用途の種類数。補完性(組み合わせの相性)とは、別の概念 |
| 同種の重なり | 同じ用途に強い店の重なり。競争が起きる材料で、減点ではない |

### 7.2 設計で悩んだ点
- **量と割合を、混同しない**: 正規化(割合)だけだと、2店舗でも6店舗でも、同じ比率なら、同じ評価になる。→ 「供給量(元の値の合計)」と「割合」を、別の値として持ち、画面・テストでも、別の列にした。重なり(同種の店の数)は、量の側の指標。
- **評価式を単純に**: 専門性は、エントロピーではなく、「一番大きい割合が、均等からどれだけ離れているか」(0〜1)。計算も説明も、1行で済む。
- **「強い適性」のしきい値**: 先に、現在の施設データを確認した。各施設に、1.0 以上の値が1つずつ(1.6 / 1.6 / 2.0 / 1.8)、次は 0.8。→ 1.0 で、きれいに分かれる。**元の適性値と比べる**(正規化後の割合とは比べない)。
- **充実度と補完性の分離**: 用途の種類数(充実度)だけを評価し、補完性は、P2-C に回した。
- **どちらかを有利にしない**: 評価は、値を返すだけで、集客・売上・品質に掛けない。ラベルも、優劣を示さない名前(日用品特化 / 混合 / 娯楽特化)にした。

### 7.3 見つけた問題と、直し方
- **パネルが、右下のメニューボタンに重なった**: 行が増えて、区画のパネルが縦に長くなり、下のボタンが隠れた(実機の画面で発見)。→ パネルの高さの上限から、下の約110を空けた(行は、縮む)。
- **削除した区画の評価が残る**: 所属の結果と評価は、同じ並びなので、片方だけ消すと、ずれる。→ 同じ添字を、一緒に消す。

### 7.4 確かめたこと
- 単体テスト(`sim_area_test`): 店なし(NaNを作らない)、元の値の供給量・割合の合計1、同じ比率で2軒と6軒 → 割合・専門性・充実度が同じで、供給量・重なりだけが違う、用途の充実度(店を増やしても増えない)、特色のラベル、専門性の式、しきい値の設定(強い適性・ラベル)、住宅・オフィスは無視、管理側の評価(区画の外の施設は数えない・削除で消える)。
- 実機(Debug): 区画を選ぶと、パネルに「施設構成」(特色・充実度のゲージ・重なり)が出る。10本のテストが成功。Debug・Release とも、新しい警告なし。
- 住民の行動は、変えていない(評価は、読み取りだけ)。

### 7.5 まだ確かめていないこと・限界
- Editor の「商業エリア」パネルの、構成の表・比較の見本は、画面では、見ていない(ビルドは通っている)。
- 施設の種類が4つだけなので、構成の幅が狭い。新しい種類が入ったら、強い適性のしきい値を、見直す。
- 数値(70% / 30% / 1.0)は、全て仮。
