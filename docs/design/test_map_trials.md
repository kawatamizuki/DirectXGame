## 決定事項(2026-11-10)
- 複数回の試行: 指定の種(基準の種)と試行の番号から、試行ごとの種を作る(`MakeTrialSeed`)。
- 決定論の確認: 最後に、1回目と同じ種で、もう1回進めて、指紋を比べる。**違う種で指紋が違うことは、合格の条件にしない**(違う種でも、同じ結果になることがある)。
- 設定値: 使った値を記録するだけ(変更・比較は、段階5以降)。
- 結果: 画面に出すだけ(ファイルへの保存は、段階4)。
- 住民の停滞などの合否判定は、しない。
- 時計の倍率: **当面20倍に固定**(暫定)。実行条件に記録する。
- 通常の耐久試験は、これまでどおり使える。

### `visitHoursLeft` の丸めの影響
- 施設の利用中(Visiting)の間だけ、毎ステップ減らし、0以下で利用を終える(`UpdateAgentMovement`)。利用を終えた後の住民には、-0.001 などの端数が残るが、次に施設へ入る時に、利用時間で上書きされる。利用中以外で、この値を読む所は、住民デバッグの表示だけ。
- 利用中の住民は、0以下になったその更新で利用を終えるので、セーブの時点で「利用中なのにマイナス」は、起きない。
- よって、読み込みで0未満を0にしても、**動きは変わらない**。E10 で、往復しても完全に同じ結果になることを確かめた。違いは、セーブのバイト(指紋)と、住民デバッグの表示だけ。→ 直す必要は無い(直すなら、利用を終えた時に0へ戻すのが筋。今回は住民AIに触れないので、しない)。

### 追記(2026-11-14): 往復の一致(E10)には、適用条件があった
- E10 の「保存→読み込みしてから進めても、完全に一致」は、**1か所ずつ・各1560ステップ**だけを確かめた結果だった。その後の追加検証(固定時間刻み F2、`docs/design/fixed_timestep.md`)で、セーブ→ロードの位置を増やすと、ずれる場合があると分かった。
- 原因: 「施設 → 商業エリア」の対応表(`DemandSystem::m_areaOfFacility`)がセーブされず、読み込みで空になり、次の需要の計算(約3秒ごと)まで作り直されない。ロード直後の約3秒に、商業エリアの施設の利用が終わる・立ち寄りを考える・週末になると、商業エリアが無いものとして動き、そこから先がずれる。
- E10 が一致したのは、たまたま、ロード直後の約3秒に、そうした出来事が無かったため。**適用条件: ロード直後の約3秒に、商業エリアに関わる出来事が無い時だけ、往復で同じ結果になる**(2026-11-14 時点。修正は承認待ち)。
- 自動検証(各試行は原本から読み込んで始める)の決定論は、影響を受けない(毎回同じように空から始まるので、同じ原本・同じ種なら同じ結果)。E1〜E9 の結論は変わらない。
- `visitHoursLeft` の丸めについての上の結論(動きに影響しない)は、正しかった(負の端数を持つのは移動中の住民で、次の施設に着いた時に上書きされる)。

### 倍率の影響(原因)
1ステップ = 実時間1/60秒 × 倍率 = ゲーム内の `dt` 秒。倍率で `dt` が変わり、次の3か所で、結果が変わる。
1. **需要の計算(3秒ごと)の回数**: `m_tickTimer += dt; if (m_tickTimer < 3.0) return; m_tickTimer = 0;` と、**3秒を超えた端数を捨てている**。`dt` が大きいほど、捨てる端数が大きく、計算の間隔が延びる。
   倍率20(`dt`=0.333)では、浮動小数の足し算で 0.333×9 が 3.0 にわずかに届かず、10ステップ(3.33秒)ごとになる = **通常の倍率1より、約1割少ない**。倍率60(`dt`=1.0)は3ステップでちょうど3秒。
   実際の間隔(float で計算): 倍率1=181ステップ=3.017秒、倍率5=37ステップ=3.083秒、倍率20=10ステップ=3.333秒、倍率60=3ステップ=3.000秒。
   E11 の抽選の回数: 倍率1=78、倍率5=77、倍率20=71、倍率60=79(同じ2週)。間隔の逆数と、ほぼ比例している。
2. **歩く・施設の利用時間**: 位置は `速さ × dt` ずつ進み、到着・利用の終わりは、ステップの区切りでしか起きない(`dt` の単位で丸まる)。
3. **時計の区切り**(就寝・起床・24時)は、`GameClock::Update` が区切りで分けて進めるので、倍率の影響を受けにくい(ここは正しい)。
さらに、**通常のプレイは、実時間のフレームの間隔(毎フレーム少しずつ違う)× 倍率** で進むので、倍率1でも、毎回わずかに違う(決定論ではない)。

### 改善の方針(段階4以降。今回は変えない)
- **固定刻み(固定タイムステップ)**: ゲーム内の時間で、1ステップの長さを決める(例: ゲーム内 1/60秒)。通常プレイでは「実時間 × 倍率」を貯めて、貯まった分だけ固定刻みのステップを回す(アキュムレーター方式)。高速検証では、描画せずに同じステップを多く回す。→ 倍率1でも20でも、同じ順番・同じ刻みになり、同じ結果になる。
- 3秒ごとの計算は、**端数を捨てずに引く**(`m_tickTimer -= 3.0`)か、ステップの回数で数える(例: 180ステップごと)。ただし、これは住民AIの結果を変える(これまでの結果と変わる)ので、ユーザーの承認と、比較の検証が必要。
- 速さの見込み: 固定刻みでは、倍率20と同じゲーム内の時間を進めるのに、ステップ数が20倍になる。diag_rt2 の104週は、今の約1.7秒 → 約35秒/回の見込み(Debug)。夜間の無人検証なら、問題にならない。
- 確かめ方: 同じ条件で「倍率1・固定刻み」と「高速・固定刻み」の指紋が一致すること。

## 今後の方針(2026-11-10 決定。今は実装しない)
### ① 倍率に左右されない結果
- 今は「1ステップ = 1/60秒 × 倍率」。倍率を上げると、1ステップで進むゲーム内の時間が長くなり(刻みが粗くなり)、結果が変わる(3-Aで、同じ種でも倍率5と20で指紋が違った)。
- 目標: 通常プレイと高速検証で、同じ初期状態・種・設定なら、原則として同じ結果。**更新の刻みと処理の順番は同じまま**、描画や待機を減らして(1フレームに多くのステップを回して)速くする。
- 最終的には、通常プレイと同じ1倍速での動作確認も必要。
- 今の作りへの配慮: 倍率は実行条件(`SimTrialConditions::timeScale`)として記録している。進め方は1か所(`SimEndurance::RunSlice` と、ゲームが渡す1ステップの関数)にまとまっているので、刻みを固定して回数を増やす方式に、置き換えやすい。
- 調べること: ふだんのプレイの刻み(実時間のフレーム間隔)と、検証の刻みの違い / 刻みを固定した時の速さ / 1倍速と高速で、指紋が一致するか。

### ② 夜間の無人自動検証
- 寝る前に、テストマップ・条件・回数を設定 → 夜の間に自動で実行 → 翌朝、ログ・統計を見る。
- 用途: 長時間の実行でのメモリリーク・異常の検出 / 抽選が設定の確率と統計的に合っているか / 住民AIの異常・長期の停滞の観察 / 複数の種・複数のマップでの長期検証 / 途中で異常終了した時の原因調査。
- 段階4〜6でログの保存・統計の比較・一括実行、段階7で画面を開かない無人実行。
- 今の作りへの配慮: 実行条件と試行ごとの結果を、データのまとまり(`SimTrialConditions` / `SimTrialResult`)で持っている(段階4で、そのままファイルに書ける)。画面は結果を読むだけで、進める処理は画面に依存しない。
- 課題: 異常の検出と指紋は、記録の仕組み(Editor のビルドだけ)を使う → 段階7で、画面なしでも記録を使えるようにする必要がある。途中で落ちた時に備えて、途中経過を少しずつファイルに書く(段階4)。
