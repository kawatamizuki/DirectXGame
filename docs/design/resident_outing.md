仕様書は暫定の試作用で、数値・式は全て仮。ここでは、**実装した範囲・仕様書から変えた点・決めた仮の動き・試し方・まだ入れていない物**をまとめる。

## 2. 週(GameClock)
| 項目 | 内容 |
|---|---|
| 1週間 | 朝6時 〜 夜10時の**活動時間**(実時間で約120秒)+ **就寝**(夜10時〜朝6時。実時間で約10秒) |
| 週末 | 就寝に入る瞬間(22時)。需要の自然減少・ペナルティの判定・施設の週の集計の区切り |
| 週の始まり | 就寝が明ける瞬間(6時)。通算の週が1つ進む。体力の回復 |
| 月・年 | 1か月=4週間、1年=12か月(`GetMonth()` `GetYear()`) |
| 時間の進み方 | 活動時間と就寝で、ゲーム内の1時間の実秒数が違う(7.5秒 / 1.25秒)。1フレームで複数の区切りをまたいでも、取りこぼさない |
| イベント | 週末・週の始まりは、回数で数えておき、使う側が `ConsumeWeekEnds()` / `ConsumeWeekStarts()` で受け取る(Editingなど、更新されない間に起きた分も、後で処理される) |
- ゲームを始める時(タイトルから)、時計を、最初の朝(第1週)に戻す(タイトルの間にも時計は動いているため)。
- 古いセーブ(週の記録が無い)は、日数を、週の数として引き継ぐ。
- 表示: HUDの時刻の横に「1年目 1月 第1週」、メニューの情報タブに、日付・今週/先週/今月の来客と売上。

## 3. 施設(FacilityData.cpp。数値は全て仮)
| 施設 | カテゴリ | 品質 | 値段 | 回復(生活/活動) | 時間 | 体力 | 適性(買い足し/まとめ買い/映画/軽食) | 敷地 | 建設費 |
|---|---|---|---|---|---|---|---|---|---|
| コンビニ(Shop) | 日用品 | 1.0 | 120 | 30 / 0 | 0.4h | 4 | 1.6 / 0.5 / 0.1 / 0.8 | 1x1 | 200 |
| スーパー | 日用品 | 1.3 | 400 | 70 / 0 | 1.0h | 8 | 0.6 / 1.6 / 0.1 / 0.4 | 2x1 | 500 |
| 映画館 | 娯楽 | 1.5 | 600 | 0 / 70 | 2.0h | 14 | 0.1 / 0.1 / 2.0 / 0.3 | 2x2 | 800 |
| カフェ | 娯楽(仮) | 1.1 | 250 | 5 / 35 | 0.8h | 5 | 0.3 / 0.2 / 0.4 / 1.8 | 1x1 | 300 |
- 品質・値段は、種類ごとの固定の値(建物ごとに調整しない)。商店街に所属しても変えない(仕様書の方針)。
- コンビニとスーパーは、**単純な上位互換にならない**よう、目的の適性を逆にしてある(買い足し=コンビニ、まとめ買い=スーパー)。
- 来訪者数・売上は、住民が実際に利用した**結果の集計**(`FacilityLedger`)。固定の売上バフは無い。

## 4. 住民の内部データ(ResidentAgent)
- 需要: 生活・アクティビティ(各0〜100。**80以上で充足**)。初期値は住民ごとに55〜100。
- 体力(`stamina`)と、上限(`traits.staminaCapBase` − ペナルティの段階 × 10)。
- ペナルティの段階(0〜3)。
- 最近使った施設の履歴(最大8件)、今の外出の状態(目的・施設・利用の残り時間・立ち寄り回数・食事系の使用フラグ)。
- **特徴(ResidentTraits。1が標準)**: 体力の上限の基準(±15%)、需要の減りやすさ(0.8〜1.25)、品質を気にする度合い(0.6〜1.5)、値段を気にする度合い(0.5〜1.6)、遠くても平気な度合い(0.7〜1.5)、自発性(0.5〜1.6)。

## 5. 外出の流れ
1. **判定**(`RunDemandTick`。約3秒おき。就寝中・20時以降は、新しく外出しない): 家にいる住民が、確率で外出を考える。需要が不足なら 0.25、足りていれば 0.03×自発性(体力50以上の時だけ)。
2. **目的**(`ChoosePurpose`): 不足があれば、より不足している需要のカテゴリ。足りていれば自発的(娯楽70%/日用品30%)。日用品は、生活が不足しているほど「まとめ買い」、そうでなければ「買い足し」。娯楽は、映画/軽食。
3. **候補**: 目的のカテゴリの施設。道路でつながっていて経路があるもの(道のりを `IPathfinder` で求める)。到達できない・体力が足りない(往復の移動+利用)ものは、**抽選の対象から外す**(理由を記録)。
4. **重み付き抽選**(`ChooseFacility`):
   `重み = 目的の適性 × 品質^(効き方×住民の係数) ÷ (1 + 値段の効き方×住民の係数×値段/基準) × exp(−道のり/(距離の目安×住民の係数))`、下限あり(到達できる候補は、無条件に0にしない)。
   魅力10と5なら、概ね2:1で選ばれる(強い方が必ず選ばれるわけではない)。
5. **歩く** → **施設の中**(施設ごとの時間。見た目は出さない) → **利用の確定**: 需要の回復・体力の消費・履歴・**来客と売上の集計・建設資金への加算** → **帰宅**。
6. 施設に着けない・経路が壊れた時は、利用扱いにしない(売上も出ない)。

## 6. 週末の処理(住民ごと)
1. **ペナルティの判定**(自然減少の前): 需要の不足が「続いている時間」が猶予(8時間)を超え、かつ、**週末になっても改善できていない(今も不足)**なら、段階+1(最大3)。週末までに改善できていれば、回避。逆に、両方が充足した状態が、10時間以上続いていたら、段階−1。
2. **需要の自然減少**(生活−35、アクティビティ−30。×住民の「減りやすさ」)。判定の後なので、**週末に新しく減った分は、その週の不足として罰しない**。
3. 継続時間を0に戻す(新しい週の不足は、ここから数える)。
- 週の始まり: 体力を、(上限まで)60回復。ペナルティ中は、上限が下がる(1段階で−10)。
- 家にいる間は、1ゲーム時間あたり2、体力が回復する。

## 12. 歩く経路(建物の出入りを、斜めにしない)
- **問題**: 道路のグラフのノードは、道路区間の端点だけ。以前は、「建物の中心 → 面している区間の**端点** → …」と歩かせていたので、長い道路の途中に面した建物から出ると、端点へ向かって、道路を斜めに横切っていた。
- **直し**(`Simulation/RoutePlanner`): 経路を「建物 → 道路上の接続点(道路に垂直) → 道路に沿って → 道路上の接続点 → 建物」にした。
  - 同じ区間に面した2つの建物は、区間の上を直接歩く。
  - 違う区間なら、両方の区間の、どちらの端点から入るか(2x2通り)のうち、道のり(接続点までの脚を含む)が一番短い組み合わせ。
  - 施設選びの「道のり」も、建物から建物までの歩く距離の全体になった(以前は、端点どうしの距離だけ)。
- 確認: 単体テスト(同じ区間・角を回る区間・端が近い方を選ぶ・端点にちょうど接する・つながっていない・逆向き。**全ての区間が、軸に平行で長さ0でない**)と、ゲームの中で、住民の位置を記録して、道路の上(z=一定)を歩き、建物の出入りだけが道路に垂直になることを確認した。

## 13. 住宅をクリックして、住民の情報を見る(ゲーム内)
- **操作**: 何も置いていない時、建物を**1回クリック**で選ぶ(黄色い枠)。**同じ住宅をもう1回クリック**すると、その住宅に住む住民の「住民の情報」パネルが開く。何も無い所のクリックで、選択が外れる。コンビニなど、住宅以外は、選ぶだけ(情報パネルは、今は出ない)。
- **時間**: パネルが開いている間は、**ゲーム内の時間が止まる**(メニューと同じ仕組み。閉じると、元の倍率に戻る)。開いた時に、UIを開く効果音が鳴る。
- **閉じる**: 「閉じる」ボタン、パネルの外のクリック、Esc、右クリック。建物・道路を置く操作を始めたり、Editingに切り替えたり、メニューを開く操作(Esc)をしたら、選択・パネルは外れる(Escは、パネルが開いている間は、パネルを閉じるだけ)。
- **中身**: 今の状態(家にいる/外出中/利用中/帰宅中)、需要(生活・アクティビティ。ゲージと、80のしきい値の目印。不足は赤)、不足・充足が続いた時間、体力(今 / 上限)、ペナルティの段階、特徴(品質・値段・遠出・自発性・減りやすさ)、直近の選択、最近の利用(施設と、週・時刻)。
- **作り**: `UI/ResidentInfoPanel`(配置と入力だけ。住民・ゲームの中身は知らない。行の一覧 `ResidentInfoModel` を見て並べる)。見た目は `IUISkin`(ゲージは `DrawGauge` を、スキンに足した)。中身の集め方は `Game::BuildResidentInfoModel`(`DemandSystem::GetResidentInfoForHome` の表示用のコピーから)。クリックの判定は、`Game::UpdateBuildingSelection`(カメラの光線と建物の箱の当たり判定。HUD・メニュー・ImGuiの上のクリックは、扱わない)。
- 確認: パネルの単体テスト(配置が画面に収まる・行が重ならない・閉じる/外/中/ImGuiの上の操作・住民がいない時)、ゲームの中で、(家の位置を画面の点にして、光線を飛ばし)クリックの判定が正しい家に当たること、パネルを開いている間、時刻が止まり、閉じると、元の倍率で進み始めること。

## 14. 住民をクリックして追跡し、住民の情報を見る
- **操作**: 何も置いていない時、**住民(歩いている小さな人)を1回クリック**すると、**追跡**に入る(カメラが、その住民を追う。足元に黄色い輪。左下に「住民を追跡中」のヒント)。**追跡中の住民を、もう1回クリック**すると、その住民の「住民の情報」パネルが開く(時間が止まる。住宅から開く時と同じ表示。副題は「住民(住宅 #N)」)。
- **追跡をやめる**: Esc、右クリック、何も無い所(地面)のクリック、建物のクリック、キー(WASD・矢印)やドラッグでカメラを自分で動かした時、建物・道路を置く操作を始めた時。ホイールのズームは、追跡中も使える(注視点は、住民のまま)。
- **建物の中にいる間**: 追跡は続く(カメラは、その住民が居る建物の位置で止まる)。見えない住民は、追跡中でなければ、クリックの対象にしない(建物のクリックを邪魔しないため)。追跡中の住民だけは、建物の中でも、その位置をクリックすると、情報が開く。
- **当たり判定**: 住民は小さいので、モデルの箱より、**全ての方向に0.12マス**大きい箱で当たりを取る(`Game.cpp` の `kAgentPickMarginLegacyCells`)。住民と建物の両方に当たった時は、**住民を優先**する。
- **カメラの追跡**: `CityCameraController` の入力に、追う点(`followActive` / `followX` / `followZ`)を足した。目標の注視点を、その点にして、なめらかに追う。ズームの後に反映するので、ズームしても、点から外れない。フィールドの範囲(+余白)の外の点は、範囲で止まる。

## 15. クリックの当たり判定の表示(F3)
- **これは、デバッグ用**。**Debugビルドだけ**で、ON/OFFできる(既定はOFF)。**Releaseには、描画のコードもスイッチも入らない**(`#ifdef ENABLE_EDITOR`)。ゲームの中の「選択・追跡のしるし」(建物=足元の黄色い四角、追跡中の住民=足元の黄色い輪)は、線だけで、当たり判定の箱ではなく、Releaseにも出る。
- **クリックの当たり判定**(Debugビルド): **F3**、または Editor > エディタ機能のON/OFF >「クリックの当たり判定を表示」で、ゲーム内(Playing)に、クリックできる範囲の箱を描く。**建物=水色、住民=ピンク(少し大きめの箱)**。選択中の建物・追跡中の住民は黄色。クリックの判定と**同じ関数**(`PickBounds`)で箱を作るので、見えている箱=実際の当たり。
- **Bounds(モデルの箱)**: 以前からある「選択中のBoundsを表示」「全てのBoundsを表示」は、以前は**Editingモードだけ**だったが、**Playingでも**描くようにした(既定はOFF)。こちらは、モデルそのままの箱(住民の余白は入らない)。
- どちらもReleaseビルドには出ない(Editorが無いため)。

## 16. 左ボタンのドラッグで、カメラを動かす
- 何も置いていない時、**左ボタンを押したまま、カーソルを動かす**と、地面をつかんで動かす(中ボタンのドラッグと同じ。WASD・矢印でも動く)。
- **クリックとの見分け**(`Core/ClickDragGesture`): 押した位置から、**6ピクセル以内**で離したら**クリック**(建物・住民の選択)。それより動かしたら**ドラッグ**(離しても、クリックにならない)。そのため、建物・住民の選択は、**ボタンを離した時**に決まる(押した位置で判定する)。
- **始まらない場合**: HUD・メニュー・パネル・ImGuiの上で押した時。建物・道路を置く操作の最中(左ボタンは、配置の道具のもの。自由描きのドラッグなど)。
- ドラッグを始めると、住民の追跡は、やめる(カメラを自分で動かした合図)。つかむ点は、押した位置(動き始めるまでの数ピクセルも、反映される)。
