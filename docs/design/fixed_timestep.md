# シミュレーションの固定時間刻みへの移行

テストマップ 段階4(結果の保存)へ進む前に、シミュレーションの時間の進め方を、ゲーム内時間の固定刻みへ変える。
技術の比較と採用の理由は `docs/study/fixed_timestep_f0_f1.md`。

## 目標(2026-11-12)
- 描画のFPS(30・60・120…)が変わっても、同じ初期状態・種・ゲーム内の経過時間なら、同じ結果。
- 速度の倍率を変えても、1回の更新で進む時間は変えない(回数だけが変わる)。
- 自動検証は、通常プレイと同じ更新を、描画・待機を省いて高速に回す。
- 3秒周期の需要の計算など、刻み・端数に依存する所も調べる。
- 住民AIの行動ルール・ゲームバランスは、時間処理と関係なく変えない。

## 調査の結果(要約)
- ループ: `TimeManager` が実時間 dt(上限なし)を測り、`Game::Update` が1フレームに1回、`GameClock::Update(dt)`(内部で ×倍率)→ `DemandSystem::Update(dt×倍率)`。倍率は 停止/1/2/4倍。ゲーム内1週 ≒ 実時間130秒(1倍。活動120秒+就寝10秒)。
- 時間に依存する所: ① 3秒ごとの需要の計算(`m_tickTimer`。3秒を超えた端数を捨てる) ② 歩き(速さ×dt) ③ 施設の利用時間・需要・体力(時計の活動時間の増分) ④ 週の区切り(時計が区切りで分けて数える。正しい)。
- 乱数: `DemandSystem` の `SimRandom` 1本だけ。描画・UIからは引かない。実時間・OSの乱数は、通常プレイの種を作る時だけ。
- 既存の固定刻みもどき(再現・巻き戻し・耐久試験・自動検証)は、どれも「実時間の刻み × 倍率」で、倍率で結果が変わる。
- 処理の重さ(住民18人、4週): 1/60秒刻みで 26,202 ステップ = Debug 81ms(1回0.0031ms)/ Release 7.7ms。倍率20の今は Debug 36ms。

## F1: 作った物
- `Core/FixedTimestep.h`(ヘッダーだけ。`GAME.vcxproj` を変えないため): 毎フレーム「実時間×倍率」を貯め、刻み(既定 ゲーム内1/60秒)の分だけ回数を出す。1フレームの実時間の上限(既定0.25秒)と回数の上限(既定240回)を超えた分は捨てる(遅くなるだけ)。補間用の割合(`Alpha`)・捨てた時間・総回数を出す。
- `GameClock::Advance(ゲーム内の秒)`: 倍率をかけずに時計を進める。`Update(dt)` は `Advance(dt×倍率)` を呼ぶだけにした(計算は同じ。単体テストで、2万回、全ての値が一致することを確認)。
- 単体テスト `tests/sim_fixed_timestep_test.cpp`: 30/60/120FPS・ばらつく間隔で同じ回数・同じ時計の状態 / 4倍で回数だけ4倍・刻みは同じ / 停止 / 長い停止の切り捨て / 回数の上限 / 補間の割合 / `Update` と `Advance` が同じ。
- ゲーム本体からは、まだ使っていない(ゲームの動きは変わらない)。

## F2: 通常プレイを固定刻みに(2026-11-12)
### 変えた所(`Core/Game.{h,cpp}`)
- `Game::UsesFixedSimulation()`: ゲームシーンの Playing で、再現(記録・再生)・巻き戻し・耐久試験が動いていない時だけ、固定刻みにする。それ以外(タイトルの背景・Editing・再現の間・巻き戻し・耐久試験・自動検証)は、今までの進め方のまま(F3でそろえる)。
- フレームの最初の `m_gameClock.Update(dt)` は、固定刻みの時は呼ばない。代わりに、住民を更新していた所で `UpdateSimulationFixed(実時間)` を呼ぶ: `FixedTimestep::Accumulate(実時間, 倍率)` の回数だけ、`RunSimulationSteps` が「時計 `Advance(1/60)` → 住民 `DemandSystem::Update`」を回す(耐久試験・自動検証と同じ順番)。
- 一時停止の条件(住民デバッグ)に当たったら、そのステップで止め、残りは回さない(貯まりも捨てる)。
- 一時停止中(倍率0)は、今までどおり、進める時間0で住民の更新を1フレーム1回だけ呼ぶ(行動テストのすぐ効く指示・住民の表示のため)。動いている間は、回数0のフレームでは呼ばない(FPSで呼ぶ回数が変わらないように)。
- 貯まりを捨てる(`Reset`): 固定刻みを使っていないフレーム(Editing・タイトル・再現など)/ 街の読み込み(`SetOnWorldReplaced`)。戻った時・読み込んだ直後に、まとめて進めない。

### 低FPSでの遅れ(上限0.25秒の仕様)
- 1フレームの実時間が0.25秒以下(4FPS以上)なら、遅れない。
- それより長いフレームは0.25秒として扱う → ゲーム内の速さ = 0.25 ÷ フレームの秒数 × 倍率(例: 2FPS で半分)。
- 回数の上限(240回)は、4倍・0.25秒でも60回なので、今の倍率(最大4倍)では効かない。
- 遅れた分は「遅くなる」だけで、結果(指紋)は同じステップ数のものと一致する。
- 普段のプレイ(60FPS上限・垂直同期)では、ウィンドウのドラッグ・読み込みなどの一時的な停止でだけ起きる(今までは、止まった時間がそのまま1回で進んでいた)。

### F3 に進む時の注意
- 再現(記録・再生)は、記録を「フレーム番号」で持っている(1フレーム=1回の更新)。固定刻みでは1フレームの回数が変わるので、「ステップ番号」で記録する形に直す必要がある。
- 巻き戻しは、遡れる長さ・キーフレームの間隔を、実時間ではなくステップ数で決め直す。倍率の変化の記録も、ステップ番号に合わせる。
- 耐久試験・自動検証は、1ステップを `RunSimulationSteps` と同じ中身(`Advance(1/60)` → 住民)にし、倍率の条件は記録だけにする。F3の後、自動検証の指紋は、F0の倍率1と一致するはず(倍率20の指紋とは変わる)。
- 時計の `Update(dt)` を使う所(タイトルの背景・Editing)は、見た目だけなので、そのままでよい。

### 見つかった問題(以前から。F2とは関係ない。2026-11-14 に修正: `docs/design/area_membership_after_load.md`)
**ロード直後の最大約3秒(ゲーム内)、商業エリアの所属が空になる。**
- 「施設 → 商業エリア」の対応表 `DemandSystem::m_areaOfFacility` はセーブされない。読み込み(`Reset`)で空にされ、次の需要の計算(`RunDemandTick`。約3秒・181ステップごと)で作り直される(`Simulation/DemandSystem.cpp:2570`)。
- その間に施設の利用が終わると、商業エリアの来訪者・売上の集計(955行目)と、立ち寄りのエリア内の補正(1136・1155・1300行目)が「エリアに属さない」として扱われる。
- 確かめた例: diag_rt2 を 21022 ステップ目でセーブ→ロードすると、56ステップ後に、ある住民の映画館の利用が、そのまま進めた方ではエリア1の来訪者に数えられ(`areasCounted: [1]`)、ロードした方では数えられない(`[]`)。そこから先がずれる。51057 ステップ目も同じ原因。
- 影響: 普段のF5→F9でも起きる。テストマップの読み込み・自動検証の開始でも起きるが、毎回同じように起きるので、決定論は崩れない(同じ原本からなら、同じ結果)。
- 直し方の案: 読み込みの最後(または対応表が空の時)に、対応表をすぐ作り直す。住民の行動の結果が変わる(ロード直後の3秒の扱いが正しくなる)ので、承認と、前後の比較が必要。

### 既知の丸め `visitHoursLeft` について(訂正と補足)
- セーブ→ロード→セーブの中身の違いは、`visitHoursLeft` の負の端数(-0.002 など)が0になる所だけだった(10か所で確認)。この端数を持っているのは、利用を終えて**移動中(外出中・帰宅中)**の住民。次の施設に着いた時に、利用時間で上書きされる(1845行目)ので、動きには影響しない。
- 3-C の「往復の忠実度(E10)」が一致したのは、たまたま、ロード直後の3秒に商業エリアの施設の利用が終わらなかったため。上の問題があるので、「往復で必ず同じになる」とは言えない(3-C の記録の補足)。
