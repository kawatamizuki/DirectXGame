# ロード直後に商業エリアの所属が空になる問題(調査と修正計画)

固定時間刻み F2 の追加検証(2026-11-14)で見つかった、**以前からの問題**(F2とは別件)。F3 の前に直す。
状態: 方式Bで修正済み(2026-11-14)・未コミット。調査・計画・試作の記録は下の1.〜6.、修正後の結果は7.。

## 1. 対応表 `m_areaOfFacility` の作成・更新・破棄
`DemandSystem::m_areaOfFacility`(`std::unordered_map<施設のid, 区画のid>`)。セーブしない(派生データ)。
| いつ | 何が起きる | 場所 |
|---|---|---|
| 破棄 | `DemandSystem::Reset()` で空にする | `Simulation/DemandSystem.cpp:175` |
| 作成・更新 | 需要の計算 `RunDemandTick` の中で、空にしてから作り直す(約3秒・181ステップごと) | 2570〜2588行目 |
| 材料 | 施設(建物のうち `IsFacility` の種類)の id・種類・敷地の四角 + 区画の一覧と設定(`m_areaSource`)→ `ComputeAreaMembers` | 同上 |
| 使う所 | 週末の評判(区画ごとの店の数)/ 施設の利用の終わり(区画の来訪者・売上の集計)/ 立ち寄り(補完性・エリア内の補正)/ 画面(区画のデバッグ) | 879・955・1136・1155・1300・3441行目 |
- `Reset()` を呼ぶのは、読み込みの中だけ(`DemandSystem::Load` と、セーブに住民の区画が無い時の `ResetToDefault`)。
- → **読み込みから、最初の需要の計算までの間(最大で約3秒)、対応表が空**。その間は、全ての施設が「どの区画にも属さない」扱いになる。

## 2. 読み込み直後に作り直す場合の、依存関係と安全性
- 読み込みの順番は、登録の順: 時計 → フラグ → 資金 → **住民(DemandSystem)→ 商業エリア**(`Core/Game.cpp:345-349`、`ScenarioManager::ApplySnapshotImpl`)。
  → `DemandSystem::Load` の中で作り直すと、**前の街の区画**を使ってしまう(安全でない)。作り直すのは、全ての読み込みが終わった後でなければならない。
- 作り直しの材料(建物・区画・区画の設定)は、読み込みが終われば全て揃っている。経路探索のグラフ・道路は要らない(軽い)。
- 需要の計算と同じ材料・同じ関数(`ComputeAreaMembers`)・同じ並び(建物の並び)で作れば、同じ結果になる(試作で確認: 下の5.)。
- 乱数は使わない。住民の状態も変えない(対応表を埋めるだけ)。

## 3. 影響する読み込みの経路
全て `ScenarioManager::ApplySnapshotImpl` → `DemandSystem::Load`(または `ResetToDefault`)→ `Reset()` を通る。
| 経路 | 入口 |
|---|---|
| F9・メニューのロード | `Game::QuickLoad` → `ScenarioManager::Load` |
| 「Scenario」パネル(Load / Load tutorial map) | `ScenarioManager::Load` |
| ゲームの開始・タイトル画面の背景 | `ScenarioManager::LoadStartScenario` |

| 巻き戻し(シーク: キーフレームの読み込み) | `GameRewind`(`LoadFromBytes`) |
→ 1か所(`DemandSystem` の中)で直せば、全ての経路に効く。

## 4. 直すと、住民AI・商業エリアの動きに出る変化
変わるのは、**読み込みから最初の需要の計算までの間(最大約3秒)だけ**。ルール・バランスは変えない(本来の動きに戻る)。
| 出来事(その約3秒の間に起きた時) | 今(バグ) | 直した後 |
|---|---|---|
| 施設の利用が終わる | 区画の来訪者・利用・売上に数えない。`areasCounted` に入らない | 数える |
| 立ち寄りを考える(補完性・エリア内の補正) | 「今いる所は区画の外」として計算 | 区画の中として計算 |
| 週末になる(評判の更新) | 区画ごとの店の数を0として計算 | 正しい店の数 |
| 外出の目的(エリア)の選択 | 影響なし(需要の計算の中で、先に作り直しているため) | 同じ |
- 読み込まない普段のプレイ(通しで遊ぶ)は、変わらない。
- 再現(再生)・巻き戻し(シーク)も、スナップショット・キーフレームの直後の3秒に同じずれがあり得たが、直すと、元の流れと同じになる。

## 5. 修正の試作で測った影響(2026-11-14、一時的な診断。試作・診断は削除済み)
| 測ったこと | 修正前 | 修正後(試作) |
|---|---|---|

| F0 の基準の指紋(倍率1・20 × 2つの街 × 2つの種、26週) | 記録どおり | **8つとも変わらない** |
- F0 が変わらない理由: F0 は、原本(ファイル)から読み込んで始める。最初の需要の計算までの約3秒に、たまたま、商業エリアの施設の利用の終わり・立ち寄り・週末が無かった。
- ただし、**別のテストマップ・別の種では、変わることがある**(原本の時点で、利用の終わりが3秒以内に迫っている住民がいる時など)。まだ結果の保存(段階4)をしていないので、比べ直す必要のある過去の結果は無い。

## 6. 修正の計画(2026-11-14 承認。方式B)
### 6.1 方式の比較(技術選定)
| 方式 | 中身 | 長所 | 短所 |
|---|---|---|---|
| A. 読み込み完了の合図で作り直す | `Game` の `SetOnWorldReplaced` から、作り直しを呼ぶ | 読み込み直後に確実 | `Game` の配線に頼る。合図を通らない使い方(単体の利用・将来の画面なし実行)で漏れる |
| **B. 印を立てて、次の更新の最初に作り直す** | `Reset` で「作り直しが必要」の印 → `DemandSystem::Update` の最初で作り直す | `DemandSystem` の中だけで完結。読み込みの順番に左右されない。画面を通らない経路(自動検証・巻き戻し・段階7の無人実行)でも必ず効く。試作で全て一致を確認 | 「読み込み → 最初の Update」の間に対応表を読む処理があれば漏れる(今は無い。画面の表示だけ) |
| C. 対応表をセーブする | セーブに所属を書く | 読み込み直後から正しい | 派生データを保存すると、区画・建物と食い違う危険。セーブ形式が変わる |
| D. `DemandSystem::Load` の中で作り直す | 読み込みの途中で作る | 単純 | 区画が後から読み込まれるので、前の街の区画を使う(危険)。登録の順番を変えると、他に影響 |
| E. 対応表をやめ、使う時に毎回計算 | キャッシュしない | ずれが起きない | 毎回の計算が重い(立ち寄りのたびに全区画×全施設) |
→ **B を採用**(試作で確認済み)。A は B の補助として不要。C・D・E は上の短所のため採用しない。

### 6.2 変更内容(`Simulation/DemandSystem.{h,cpp}` だけ)
1. 所属を作る処理を、1つの関数にまとめる(需要の計算の中の処理と、読み込み後の作り直しで、同じ関数を使う。結果が食い違わないように)。
2. `Reset()` で「作り直しが必要」の印を立てる。`Update()` の最初で、印があれば作り直す(需要の計算でも、作り直したら印を下ろす)。
3. 区画・建物の変更(区画の移動・建築・解体)の後の約3秒の遅れは、今までどおり(今回の対象外。別の問題として記録)。

### 6.3 確かめ方(回帰テスト)
- **単体テスト**: 所属を作る関数(画面に依存しない部分)に、`tests/` のテストを足す(区画の中・外・境界の施設)。
- **ゲームの中の診断**(一時的。確認後に削除): 上の5.と同じ。① 40ステップごとのセーブ→ロード(2つの街 × 1491か所)が全て一致 ② 再現条件の2か所(21022・51057)が一致 ③ F0 の指紋が変わらない(変わる場合は、変わった試行と理由を記録)④ 自動検証・耐久試験・再現・巻き戻しが、今までどおり動く。
- (提案・任意)**常設の回帰テスト**: 「セーブ→ロードの往復テスト」を、耐久試験のパネルに足す(原本から進めながら、一定間隔でセーブ→ロードし、そのまま進めた結果と比べる)。夜間の無人検証(段階7)でも使える。ただし範囲が広がるので、別の段階として相談したい。

### 6.4 F0 の基準の指紋の扱い
- 試作では、F0 の8つの指紋は変わらなかった。本番の修正でも変わらないはず(同じ処理)。変わった場合は、どの試行が・なぜ変わったか(最初の3秒の出来事)を記録し、F0 の表に「修正後」の列を足す。

## 8. 別件として記録(今回は変えていない)
**建築・解体・商業エリアの変更の後、所属の更新が最大約3秒遅れる。**
- 所属は、需要の計算(約3秒ごと)でしか作り直さない。施設を建てた直後・壊した直後・区画を動かした直後は、次の計算までの間、古い所属で動く。
- 読み込み直後(今回直した)とは別の問題。直すなら、建築・解体・区画の変更の時にも「作り直しが必要」の印を立てる方法がある(今回の仕組みを使える)。住民の行動の結果が変わるので、承認と比較が必要。
